### Priority Visual Language (GOALS-02 — new in Phase 14)

Priority must be visually distinct at all three levels and consistent across GoalCard (Goals screen) and ChunkCard (Schedule screen). Color alone is not sufficient — each level uses color + icon + label so the distinction is accessible without relying on color perception.

**Priority tier definitions:**

| Tier | `priorityWeight` | Chip/Badge Color | On-Color | Icon | Label |
|------|-----------------|-----------------|---------|------|-------|
| Low | 0.25 | `colorScheme.surfaceContainerHighest` | `colorScheme.onSurfaceVariant` | `Icons.arrow_downward` (size 12) | "Low" |
| Normal | 0.5 | (none — no chip shown) | — | — | (omitted) |
| High | 0.75 | `colorScheme.primaryContainer` | `colorScheme.onPrimaryContainer` | `Icons.arrow_upward` (size 12) | "High" |

Design rationale: Normal priority is the default for every goal. Showing a chip only for Low and High means the chip's presence communicates deviation from the norm — no chip = normal. This keeps the card visually clean when all goals are at normal priority while making outliers obvious.

**Priority chip widget spec (GoalCard):**

```
Container(
  padding: EdgeInsets.symmetric(horizontal: 6, vertical: 2),
  decoration: BoxDecoration(
    color: chipColor,          // tier-specific from table above
    borderRadius: BorderRadius.circular(10),
  ),
  child: Row(
    mainAxisSize: MainAxisSize.min,
    children: [
      Icon(icon, size: 12, color: onColor),
      SizedBox(width: 3),
      Text(label, style: textTheme.labelSmall?.copyWith(
        color: onColor,
        fontWeight: FontWeight.w500,
      )),
    ],
  ),
)
```

Chip height with 2dp vertical padding + 12sp text = approximately 20dp. Meets no minimum-tap-target requirement because chips are not interactive (display only).

**Priority chip placement in GoalCard:**

Place the priority chip at the end of the secondary-line row. If there is no secondary line (outcome goal type with no streak/budget stat), show the chip as a standalone row below the goal name with `SizedBox(height: 4)` above it. Never place the chip in the title row (it conflicts with the color swatch and hover icons).

```
// In GoalCard column:
Row(title icon + name + color swatch/hover gate)  // existing
if (secondary != null || showPriorityChip) ...[
  SizedBox(height: 4),
  Row(
    children: [
      if (secondary != null)
        Expanded(child: Text(secondary, style: textTheme.bodySmall)),
      if (showPriorityChip) _PriorityChip(priorityWeight: goal.priorityWeight ?? 0.5),
    ],
  ),
]
```

`showPriorityChip` = `(goal.priorityWeight ?? 0.5) != 0.5` — hide chip at normal weight.

**Priority badge in ChunkCard and ActiveChunkCard:**

On the schedule, the goal's priority is communicated via the left-edge color bar intensity, not a separate chip (the bar color is already the goal color). Instead, add a minimal priority badge — same chip spec as above — in the top-right area of the content column, replacing the `Icons.radio_button_unchecked` status icon position when the chunk is unresolved.

Wait — the status icon already occupies the top-right. Do NOT stack the priority badge on top of the status icon. Instead, place the priority badge **below the clock-time line**, as an inline small chip on the same row as `displayRationale`:

```
// After clock-time text in _WorkChunkContent's inner Column:
if (priorityLabel != null) ...[
  SizedBox(height: 2),
  _PriorityChip(label: priorityLabel, chipColor: chipColor, onColor: onColor, icon: icon),
]
```

The `displayRationale` row and the priority chip row are separate lines — rationale first, then priority chip. Both use `bodySmall` / `labelSmall` scale, so the visual weight matches.

For `ActiveChunkCard`, the same pattern applies: priority chip appears below the clock-time line, above the Complete/Skip action row.

`ChunkCard` and `ActiveChunkCard` receive `goalPriorityWeight` as a new named parameter (`double? goalPriorityWeight`). Both callers (ScheduleScreen's ListView builder and HomeScreen's ActiveChunkCard) look up the goal from `GoalsNotifier.goals` by `chunk.goalId` and pass the `priorityWeight`. Commitment chunks have `chunk.goalId == null` — pass `null`, which means no priority badge is shown.

## Goals Screen Redesign Contract (GOALS-01)

### Current problems (from codebase audit)

1. **No heading**: The AppBar says "Goals" but there is no subheading or framing copy that explains this screen's purpose as a prioritization view.
2. **Drag handle ambiguity**: On desktop, `Icons.drag_handle` (two horizontal lines) at 60% opacity is the reorder affordance. The dogfood noted this was "ambiguous two slashes" — users cannot tell if it is a drag handle, a menu icon, or decoration.
3. **No priority display**: GoalCards show goal name + secondary stat but nothing about priority. A goal's priority weight is invisible to the user after they set it in the form.
4. **Mobile reorder hidden**: On Android/iOS, long-press-to-drag has no visible affordance at all. The user has no indication they can reorder goals.

### Fixes

#### 1. Screen heading (GOALS-01 — purpose explicit)

Add a `SliverToBoxAdapter` as the first sliver in `CustomScrollView`, before any section headers, containing:

```
Padding(
  padding: EdgeInsets.fromLTRB(16, 16, 16, 4),
  child: Column(
    crossAxisAlignment: CrossAxisAlignment.start,
    mainAxisSize: MainAxisSize.min,
    children: [
      Text(
        'Your goals',
        style: textTheme.titleMedium?.copyWith(fontWeight: FontWeight.w600),
      ),
      SizedBox(height: 4),
      Text(
        'Drag to prioritize. Tap to edit.',
        style: textTheme.bodySmall?.copyWith(color: colorScheme.onSurfaceVariant),
      ),
    ],
  ),
)
```

This heading appears only when goals exist (not in empty state). When all sections are empty, the `_EmptyState` widget occupies `SliverFillRemaining` as before.

Copy rationale: "Drag to prioritize" names the primary action. "Tap to edit" removes ambiguity about card tap behavior. Lowercase, direct, no punctuation flourish.

#### 2. Drag handle — mobile and desktop clarity (GOALS-01 — reorder affordance obvious)

**Desktop (existing but improved):** Change the drag handle icon from `Icons.drag_handle` to `Icons.drag_indicator` (six dots in a 2×3 grid — universally recognized as a drag affordance). Keep the existing `AnimatedOpacity(opacity: 0.6)` wrapper and `ReorderableDelayedDragStartListener`. Keep the `Padding(symmetric(horizontal: 8))` wrapper. Ensure the icon's total touch target is `SizedBox(width: 44, height: 44)` wrapping the icon (the icon itself is 24dp; 44dp padding satisfies the minimum).

**Mobile (new):** On `TargetPlatform.android` / `.iOS`, the current code passes `trailing: null` to GoalCard, which hides the drag affordance entirely. Replace with a visible-but-subtle long-press hint:

```
// In GoalsScreen._buildReorderableSection, isMobileTouch branch:
trailing: ReorderableDelayedDragStartListener(
  index: i,
  child: Padding(
    padding: EdgeInsets.symmetric(horizontal: 8),
    child: Icon(
      Icons.drag_indicator,
      size: 20,
      color: colorScheme.outlineVariant,  // lighter than desktop — subtle on mobile
    ),
  ),
),
```

On mobile, the handle is always visible at `colorScheme.outlineVariant` opacity (lighter than desktop's `colorScheme.outline`). The `ReorderableDelayedDragStartListener` still requires a long-press to initiate drag — the visible icon simply tells the user reordering is possible.

**Tooltip:** Wrap the desktop `ReorderableDelayedDragStartListener` in `Tooltip(message: 'Drag to reorder')` so hovering on desktop shows the affordance label.

#### 3. Priority display on goal cards (GOALS-02)

See §Priority Visual Language above. GoalCard gains the priority chip in its secondary row.

#### 4. Reorder updates priority weight (GOALS-01 + PRIORITY-01)

Currently `GoalsNotifier.reorder()` only updates `sortOrder`, not `priorityWeight`. This means drag-reordering does NOT change scheduling behavior — reordering is purely cosmetic with no engine effect.

This phase must change `GoalsScreen._buildReorderableSection` to call `reorderAllWithPriority` instead of `reorder` when a drag completes. Since `reorderAllWithPriority` takes a flat ordered ID list across ALL goals (not just the type group), the caller must reconstruct the full ordered list:

```
onReorderItem: (oldIndex, newIndex) async {
  // 1. Perform visual reorder within the type group (compute new group order).
  final reorderedGroup = [...group];
  final item = reorderedGroup.removeAt(oldIndex);
  reorderedGroup.insert(newIndex, item);

  // 2. Build full ordered ID list: all type groups in display order,
  //    with this group's goals replaced by reorderedGroup.
  final allOrdered = _buildFullOrderedIds(notifier, type, reorderedGroup);

  // 3. Write sortOrder + priorityWeight atomically.
  await notifier.reorderAllWithPriority(allOrdered);
},
```

`_buildFullOrderedIds` reconstructs the flat list using the existing display order of the other groups and the newly reordered group. The order is: timeTargetGoals (reordered if `type == GoalType.timeTarget`) + outcomeGoals (reordered if outcome) + habitGoals (reordered if habit).

**Important:** The `priorityWeight` from `reorderAllWithPriority` applies a linear spread (0.75 top → 0.25 bottom) across ALL goals regardless of type. This is intentional — it allows the schedule engine to compare priority across goal types.

**Side effect awareness:** A user who explicitly set a goal's priority in the form to "Low" (0.25) may find that drag-reordering changes that value. This is by design: reordering is the primary prioritization gesture; the form's SegmentedButton is a secondary explicit control. The last write wins. The form's SegmentedButton still saves directly to `priorityWeight` via `saveGoal()` — this is not changed.

## Priority Engine Contract (PRIORITY-01)

### Current engine behavior

In `schedule_generator.dart`:
- Step 3 (outcome goals): `urgencyScore = priorityWeight / daysRemaining`. Priority is part of the urgency formula — it already has a real effect for outcome goals.
- Step 4 (time-target goals): priority is a tiebreaker only (`(b.priorityWeight ?? 0.5).compareTo(a.priorityWeight ?? 0.5)` when remaining hours differ by < 0.01). For time-target goals with meaningfully different remaining hours, priority has no effect.
- Step 2 (habits): no priority sorting at all — habits appear in the order they appear in `activeGoals`, which reflects `sortOrder` from the notifier.

### Required change (PRIORITY-01)

For the engine to meet success criteria 3 and 4 (changing priority produces measurably more/earlier/fewer chunks), priority must influence chunk allocation in a way visible to the user without inspecting code. The minimum change is:

**Step 4 (time-target goals):** Add `priorityWeight` as a primary multiplier on demand chunks, not just a tiebreaker. Replace:
```dart
// current sort: most-behind first, priority as tiebreaker
timeTargetGoals.sort((a, b) {
  final remA = _remainingHours(a, ...);
  final remB = _remainingHours(b, ...);
  if ((remA - remB).abs() > 0.01) return remB.compareTo(remA);
  return (b.priorityWeight ?? 0.5).compareTo(a.priorityWeight ?? 0.5);
});
```
With a composite score that combines remaining hours AND priority:
```dart
// new: composite score — remaining hours * priorityWeight → higher = more chunks first
double score(Goal g) =>
    _remainingHours(g, completionLogs, date) * (g.priorityWeight ?? 0.5);
timeTargetGoals.sort((a, b) => score(b).compareTo(score(a)));
```
This means a high-priority time-target goal with moderate remaining hours ranks higher than a low-priority goal with the same remaining hours. The `_demandForTimeTarget` calculation (`remaining × 60 / 25 / daysLeft`) is unchanged — multi-chunk demand is still budget-driven. Priority changes which goals fill the cap first.

**Step 2 (habits):** Sort habit goals by `priorityWeight` descending before iterating:
```dart
final habitGoals = activeGoals
    .where((g) => g.goalType == GoalType.habit)
    .toList()
  ..sort((a, b) =>
      (b.priorityWeight ?? 0.5).compareTo(a.priorityWeight ?? 0.5));
```
This ensures a high-priority habit appears in the schedule before a low-priority habit when both are due and cap is constrained.

These changes are the engine contract that the planner must implement. The UI spec's job is to define what the user sees that makes the change observable.

### What makes the change observable (UI side)

The user observes priority effects through:
1. **Priority chip on goal card**: After setting a goal to High, the orange chip appears on the goal card. After regenerating, chunks from that goal appear earlier in the schedule (higher synthetic start time due to cap fill order).
2. **Priority badge on chunk card**: The High/Low badge on chunk cards confirms which goal the chunk belongs to and reinforces why one goal's chunks appear before another's.
3. **Rationale text**: Existing rationale strings ("2.0h behind this week", "Deadline in 3 days") already communicate why a goal was scheduled. Priority does not need its own rationale string — the chip on the card is the visual anchor.

There is no "priority changed" notification or confirmation dialog. The effect is visible purely through the regenerated schedule.

## Accessibility Contract

- Priority chip must not rely on color alone: each level uses icon (arrow up/down) + label text in addition to background color.
- Normal priority has no chip — absence of chip is a valid null state, not an error state. Screen readers will not encounter an unlabeled chip.
- Drag handle icon (new: `Icons.drag_indicator`): wrap in `Semantics(label: 'Drag to reorder', button: false)` so screen readers can announce it.
- Priority badge on chunk cards: same color-independent rule — icon + label text.
- GoalCard chip is display-only; no `GestureDetector` needed, no focus required.
- Minimum touch targets: drag handle icon wrapper is `SizedBox(44, 44)` — compliant. GoalCard `InkWell` fills card height ≥ 48dp on any goal with a name + secondary stat — compliant.
- Section headers ("Regular time" etc.) are `Text` widgets in `colorScheme.primary` — primary on surface passes WCAG AA.
