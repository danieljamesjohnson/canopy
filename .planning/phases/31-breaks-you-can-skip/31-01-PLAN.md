<objective>

accepts a leftward drag started inside an invisible 16dp band above its painted top edge, and
that drag calls `ScheduleNotifier.markSkipped` for that break — without moving or resizing a
single painted pixel.

This is the phase's tracer slice. It touches every layer the phase will modify (geometry

<planner_decisions>

These are decided here, not left to the executor. Each is a deliberate choice with a stated
reason; do not relitigate them mid-execution, and do not silently deviate.

**PD-31-01 — the defensive per-neighbour slop clamp is OMITTED. Slop is symmetric.**
`31-UI-SPEC.md` sketched `topSlop = clamp(kBreakHitSlop, 0, precedingRowSlot / 2)` and a matching
`bottomSlop`. This plan applies the full `kBreakHitSlop` on BOTH sides with no clamp, for three
reasons, in order of weight:

1. **Asymmetric slop would break SKIPBREAK-02.** The painted content is centred inside the grown
   box with `Align(alignment: Alignment.center)`. Centring places the painted band at
   `(topSlop + bottomSlop) / 2` from the grown box's top. That equals `topSlop` only when the two
   are equal. An asymmetric clamp would silently shift the painted row by up to 8dp off
   `geometry.yFor(start)` — the exact class of "the timeline lies about when something happens"
   this phase exists to avoid.
2. Today's lattice sandwiches every break between work chunks of 25 minutes or longer (100dp at
   `kPixelsPerMinute = 4.0`), so the clamp is dead code — it can never bind (`31-RESEARCH.md`
   Assumption A2, Open Question 2, which recommends exactly this).
3. Threading `precedingRowSlot`/`followingRowSlot` through `_buildPositionedRow` would add sibling
   context to a load-bearing, heavily-commented dispatch function for no live benefit.

This omission is deliberate and must be recorded in a doc comment beside `kBreakHitSlop`, not
left silent. If a future lattice change ever puts a chunk under 32dp next to a break, the
symmetric-slop assumption needs re-deriving — say so in the comment.

**PD-31-02 — the paint confinement lives in `SwipeableChunkCard`, via a new `visualHeight`
parameter.** `31-UI-SPEC.md` allowed either split. It must live here, because the confinement has
to wrap the `Dismissible`'s `background` **and** its `child` independently, and the `background`
is constructed inside `SwipeableChunkCard` where `today_screen.dart` cannot reach it. The
alternative (building a second `Dismissible` in `today_screen.dart`) duplicates the gesture
wiring — the exact hand-rolling `31-RESEARCH.md` § "Don't Hand-Roll" argues against.

**PD-31-03 — `ClipRect` + `OverflowBox` move INSIDE `SwipeableChunkCard` for the confined case;
`TimelineRowTile` stays outside.** `TimelineRowTile` is a pure horizontal-inset wrapper
(`Padding` -> `Row(crossAxisAlignment: start)` -> gutter + `Expanded`), so it composes correctly
at the grown height and keeps the reveal inset consistent with every other row. `ClipRect` and
`OverflowBox` are Flutter built-ins with no import-layering cost. `SwipeableChunkCard` must NOT
import `TimelineRowTile` — that would reach from `screens/schedule/` into `screens/today/`.

**PD-31-04 — every break row goes through the new arm, not just slop-bearing ones.** `visualHeight`
is passed for every break at every density; the slop itself is `0.0` unless
`slot < kMinBreakDragTarget`. One rule, not two: it makes the reveal icon size uniform across
break tiers and keeps the non-slop case an exact identity transform (grown height == slot,
`Align(center)` is a no-op). Only slop-bearing breaks move to the Layer 1b Stack pass.

**PD-31-05 — the reveal for a break is supplied as `background`, NOT `secondaryBackground`.**
`31-PATTERNS.md` flagged this as needing verification and guessed the opposite way. Verified
against the SDK this session: `Dismissible`'s constructor carries
`assert(secondaryBackground == null || background != null)` (`dismissible.dart:118`), so
`secondaryBackground` can never be supplied alone; and `_DismissibleState.build`
(`dismissible.dart:613-619`) only substitutes `secondaryBackground` **when it is non-null**,
otherwise using `background` for every direction including `endToStart`. In the unified widget
below this resolves to: `background` always non-null, `secondaryBackground` non-null only for
work chunks.

**PD-31-06 — a live break is deliberately, explicitly out of scope.** A break that is currently
running renders through `_buildLiveRow` -> `LiveRowCard`, whose `showActions:` argument at
`today_screen.dart:979` is work-chunk-only. That is a pre-existing gap, not one this phase
introduces (`31-RESEARCH.md` Pitfall 4, Open Question 1). Leave that call site byte-for-byte
unchanged. This exclusion is recorded, not silent, and is surfaced to the owner in plan 31-05's
UAT rather than assumed away.
</planner_decisions>

<assumption_delta_decision>
**Assumption losing its monopoly:** `SwipeableChunkCard` currently branches on
`chunk.chunkType != ChunkType.work` and returns a bare `ChunkCard` for everything else — the
identity model "work chunks are the resolvable thing; everything else is inert."

**The noun that is now primary:** *a resolvable chunk row* — every timeline chunk row is wrapped
in a `Dismissible` that at minimum supports skip.

**Decision: `promote`.**

The `chunkType != work` early return is **deleted**, not paired with a sibling branch. The widget
returns exactly one `Dismissible` for every chunk type. Work-chunk-ness demotes to three additive
details of one variant, each expressed as a single conditional on a local `isWork`:

- `direction` gains the `startToEnd` half (`DismissDirection.horizontal` instead of `endToStart`)
- `secondaryBackground` (the second reveal) is supplied
- `onTap` is forwarded

**Rationale for promote over add-alongside:** an add-alongside would leave two parallel
`Dismissible` constructions to keep in sync — two `confirmDismiss` closures, two reveal
definitions, two `direction` rules — and the next person to change skip behaviour would have to
find both. It is also what the phase actually means: skippability is now the general case and
completability is the special case, so the code should say that. The owner's explicit
restrictions (`onTap` and the complete direction stay work-only) survive intact as variant
details — that is precisely a demotion of the specific, not a preservation of its privilege.

**Not accepted debt.** Nothing is deferred by this decision. The one thing it makes easy to get
wrong is `onTap`: `today_screen.dart:_buildChunkCard` already passes a non-null `onTap` for
*every* unresolved chunk including breaks, and today it is the deleted early return that discards
it. After the promote, the `isWork` gate is the only thing keeping breaks untappable — so that is
covered by an explicit acceptance criterion and a widget test in Task 2, not by inspection.
</assumption_delta_decision>
