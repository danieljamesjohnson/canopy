<objective>
Route the live row through the same positioning path every other row already uses, and give
`LiveRowCard` the two density tiers that let it survive both a 100dp slot and a 20dp one.

Purpose: GRID-02. Plan 27-01 stopped the geometry from reserving extra height; without this plan
the live card overflows into the rows beneath it. The spike proved that simply letting it clip
(variant b) deletes the countdown mid-glyph and both action buttons — the current activity becomes
the one row in the day you cannot act on. Compaction is the settled answer.

Output: `LiveRowCard` with a required `slotHeight` and two tiers; the live row's `Positioned`
carrying a duration-exact `height:`; the progress bar and "Next ·" line gone; single-line work
chunks reachable via tap.
</objective>

<locked_planner_decisions>
Read these before starting. Four of them resolve genuine conflicts or gaps in the source
documents; do not re-decide them and do not "correct" them back toward the source text.

- **PD-27-01 — the single-line tier's margin is zero VERTICALLY ONLY.** `27-UI-SPEC.md` says
  `margin: EdgeInsets.zero` "(all four sides)", but every word of its justification is about
  height: "the smallest guaranteed slot (20dp) cannot spend any of its height on margin and still
  leave room for one legible text line." Zeroing the HORIZONTAL margin would bleed the card to the
  raw viewport edge — the exact previously-shipped regression `timeline_row_tile.dart`'s own doc
  comment records ("the live row bled to the raw screen edge"), because the live row is positioned
  `left: 0, right: 0` with no `TimelineRowTile` and therefore inherits no inset. The spike's own
  `_buildSingleLine` kept both horizontal insets. **Use
  `EdgeInsets.only(top: 0, bottom: 0, left: kCardLeftInset, right: kTimelineRowInset)`** — the
  spec's stated intent, exactly, with its unstated horizontal consequence declined.
- **PD-27-02 — `progress` is deleted along with the bar.** `27-UI-SPEC.md` drops the
  `LinearProgressIndicator` from the compact tier and the single-line tier never had one, so
  `LiveRowCard.progress` and `_buildLiveRow`'s progress computation become passed-but-never-
  rendered dead code — the same class `27-RESEARCH.md` Pitfall 4 flags for `nextLine`, which
  `flutter analyze` cannot catch. Both go. `_liveSecondsRemaining` is UNTOUCHED: it still feeds
  `remainingLabel` and `_syncFastTimer`, and it is the single-source contract (P-5).
- **PD-27-03 — `nextLine` is deleted outright**, resolving `27-RESEARCH.md`'s open question A2:
  the parameter, its `nextChunk` lookup in `_buildLiveRow`, and the `Text` that renders it.
  Neither locked tier has a home for it, and the spike's reasoning holds — the next row is now
  literally drawn immediately below this one. `_chunkTitle` itself SURVIVES: it still has two
  callers at `today_screen.dart` ~460 (PreStart) and ~507 (GapBeforeNext).
- **PD-27-04 — the single-line tier's `Semantics` must keep the tap accessible.**
  `27-UI-SPEC.md` locks `Semantics(label: 'Right now: $title, $remainingLabel',
  excludeSemantics: true)`. `excludeSemantics: true` strips the subtree's semantics INCLUDING an
  `InkWell`'s button role and tap action, which would make the single-line work chunk's only
  affordance invisible to a screen reader. Put `button: onTap != null` and `onTap: onTap` on the
  `Semantics` widget itself, alongside the locked label. This is the same class of correction
  Phase 26 made at `26-04` (PD-13) when `IgnorePointer` silently ate the now-line's announcement.
- **PD-27-06 — the screen always supplies `onTap` for an unresolved live WORK chunk; the card
  wires it only in `_buildSingleLine`.** Tier selection lives in the card, so the screen cannot
  know which tier will render. The compact tier has explicit icon buttons and deliberately ignores
  `onTap`. A live BREAK gets `onTap: null` in both tiers — `27-UI-SPEC.md`: "no tap target at all."
</locked_planner_decisions>
