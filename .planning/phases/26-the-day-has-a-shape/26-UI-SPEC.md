## Architecture: from a row list to a positioned overlay (foundational — read first)

D-01's consequence note says `NowMarkerRow`'s between-rows insertion is "reworked, not
extended." Here is what that means concretely, because it drives every other decision below:

**Why a between-rows row can no longer represent "now."** `NowMarkerRow` worked as a
list item because the old marker only ever needed to sit at a chunk *boundary*. CAL-02
requires the line to sit at an arbitrary point **inside** a chunk's rendered span (e.g. 12
minutes into a 25-minute chunk). A `ChunkCard` is one monolithic widget — there is no way to
"insert a row" partway through it. The only architecture that can place a line at an arbitrary
fractional position over arbitrary content is an **absolutely-positioned overlay**, computed
from a pixel offset, not a list position.

**The model.** Every `TimelineRow` (chunk, leading-free, gap-free) already carries or can
derive a `durationMinutes`. The render layer computes each row's pixel height as
`durationMinutes * kPixelsPerMinute` (declared below) and lays the day out as a single `Stack`
inside the existing `SingleChildScrollView`/`_dayScrollController`:

1. **Layer 1 — rows.** A `Column` of duration-sized boxes in clock order (each row wrapped so
   its allocated height is exactly `durationMinutes * kPixelsPerMinute`, with the one named
   exception below for the live row). This is the scroll content and it owns total height.
2. **Layer 2 — hour axis.** A set of `Positioned` hour-boundary labels + hairlines, at
   `top: (hourMinutes - rangeStart) * kPixelsPerMinute`, painted **behind** layer 1's card
   fills (see "The time gutter becomes an hour axis" below). Wrapped in `IgnorePointer`.
3. **Layer 3 — the now-line.** One `Positioned` overlay at
   `top: (nowMinutes - rangeStart) * kPixelsPerMinute`, painted **above** everything, wrapped
   in `IgnorePointer` so it never intercepts a Complete/Skip tap underneath it.

`nowMinutes` is **not** a `TimelineRow` any more — `buildTimeline` stops emitting a
`NowMarkerRow` entirely. It becomes a plain value threaded straight from `build()`'s existing
single `nowDt` sample to the render layer, exactly the same seam `nowMinutes` already is today
— only its destination changes (an overlay offset calculation instead of a list-insertion
check). This keeps the single-clock-sample rule (CAL-02 success criterion 4) intact by
construction: there is still exactly one `nowDt` read in `build()`, and the line is arithmetic
derived from it, never a second opinion.

**Suppression is gone, not relocated.** Phase 24's `nowState is! Active` guard is deleted, not
moved. The line renders in every state — `PreStart`, `Active`, `Overdue`, `GapBeforeNext`,
`DayComplete` — because "rendered range always contains `nowMinutes`" (see Scroll-on-open
below) makes it always representable.

## The pixels-per-minute scale (CAL-01) — `kPixelsPerMinute = 4.0`, fixed

> **Amendment, 2026-08-10 (Plan 01, PD-1) — `kPixelsPerMinute` corrected to
> `5.5`, superseding `4.0` below.** The `4.0` rationale text that follows
> claimed a 25-minute work chunk renders `100px`, "enough for a trimmed
> Full-tier card (title + time range + action row)." That claim is
> measurably false: a `ChunkCard` work card carrying exactly title + time
> range + the Complete/Skip row, rendered at a width wide enough that no
> text wraps, measures **126.0px** (measured 2026-08-10 via
> `tester.getSize(find.byType(ChunkCard))`). At `4.0` every standard
> 25-minute chunk would overflow its slot by 26px. `5.5` gives `137.5px`
> for 25 minutes — fits with ~11px of slack — and a 12-hour day still
> renders ~3960px (≈5 mobile screens), squarely inside D-02's "the user
> scrolls through it." Also measured: `LiveRowCard`'s real height is
> **230.0px** (the range below's "200–220px" estimate was low), which sets
> `kLiveRowReservedHeight = 240.0`. The density-tier thresholds below
> (`Full` at `≥ 20 min` / `≥ 80px`, `Compact` at `< 20 min` / `< 80px`) are
> now expressed in **pixels**, not minutes — `kFullTierMinHeight = 132.0`
> for work chunks, `kFullBreakMinHeight = 88.0` for breaks — so the
> threshold doesn't silently rot if the scale is ever corrected again. See
> `lib/screens/today/timeline_geometry.dart` and `26-01-PLAN.md`'s "Locked
> planner decisions" (PD-1/PD-2/PD-3) for the full reasoning. The original
> `4.0` rationale text below is left unmodified as the reasoning trail —
> this note supersedes it, not replaces it.

**Fixed, not responsive to viewport height.** Responsive-to-fit (scaling so the whole day
always fits one screen) would eliminate scrolling — which directly contradicts D-02's own
wording ("the user scrolls") and CAL-03 ("reaching \[the past\] is a deliberate scroll"). A
fit-to-viewport scale would also make the same clock position map to a different pixel
position on a phone vs. a desktop window, which turns "shape" into a device-dependent
illusion rather than a real one. `kPixelsPerMinute` is therefore a single constant, identical
across every platform this app ships to.

**Why 4.0, not something smaller or larger:**

- At `4.0`, a full mood-3 cadence cycle (four 25-min chunks + their 5-min short breaks, then a
  25-min long break — `120 + 25 = 145 min`) renders `580px` tall — a little under one mobile
  viewport. A realistic 10–12 hour day (8am–6/8pm) renders `2400–2880px`, roughly 3–4 mobile
  screens of scrolling. That is "a day has a shape you scroll through," not "a day that never
  ends" and not "a day that fits without scrolling" (which would defeat CAL-03).
- At `4.0`, a 25-minute work chunk or long break renders `100px` — enough for a trimmed
  **Full**-tier card (title + time range + action row, see below) without needing a rescue
  clamp. A smaller scale (e.g. `2.0` → `50px`) cannot fit an action row at all for the single
  most common chunk duration in the app; a larger scale (e.g. `8.0` → `200px`) roughly doubles
  total scroll length for no legibility gain once the Full tier already fits.
- A 5-minute short break renders `20px` — deliberately small. That is not a bug to engineer
  around; it is CAL-01's whole point ("a thin gap is legible without reading times"). Its
  legibility at that size is handled by content degradation, not by inflating the scale to
  rescue it (see next section).

**Interaction with D-02 ("no min/max row-height clamping"):** that prohibition is honored
literally — no row's *container* height is ever floored or ceilinged independent of its
duration. What changes at small sizes is the *content rendered inside* an already
duration-sized box (density tiers, below) — the box itself is never inflated to make room.

## Row content density (CAL-01 + must-specify #2) — the 5-minute-break case

Two tiers, keyed on `durationMinutes`, not on chunk type — the threshold is what determines
whether the box is tall enough for the current full treatment, not what kind of chunk it is:

| Tier | Duration | Height @ 4px/min | Trigger |
|------|----------|-------------------|---------|
| **Full** | ≥ 20 min | ≥ 80px | Every current work chunk (25 min) and long break (25 min) |
| **Compact** | < 20 min | < 80px | Short breaks (5 min); any unusually short generated chunk |

### Work chunk, Full tier (≥80px)
Title (`titleMedium`/16px 600, single line, ellipsis) + time range (`bodySmall`,
`formatTimeRange`) + action row (`Complete`/`Skip`, unresolved) or a status icon (resolved).
**Rationale text, the priority chip, and the valence chip are dropped from the row** — they
remain fully available in `ChunkDetailSheet` (unchanged, opened by tap). This is a deliberate
trim, not a regression: at `100px` for the modal 25-minute case there is not room for every
badge the pre-proportional card carried, and CAL-01's job is "shape at a glance," not
"every attribute at a glance" — the detail sheet already exists for that.

### Work chunk, Compact tier (<80px)
Title only (`bodyMedium`, single line, ellipsis). No time text (redundant with the hour axis
+ its own position — see below). No inline action row — Complete/Skip live in
`ChunkDetailSheet`, reached via the row's own tap (the full row width × its slot height is the
hit target; `ChunkDetailSheet` already carries Complete/Skip/Defer for any unresolved chunk,
so nothing new is built here, only reached via a shorter row). This tier should be rare in
practice — the schedule generator's default chunk size is 25 minutes — but the rule must exist
because nothing in this codebase currently guarantees a work chunk can't be shorter.

### Break, Full tier (long breaks, 25 min → 100px)
Unchanged from the current `_buildBreak` treatment: icon + title (`titleMedium`/500) +
duration text, dashed outline, 24dp vertical padding. No change needed — it already fits.

### Break, Compact tier (short breaks, 5 min → 20px)
Label only (`bodySmall`, "Short break" or "Long break" as applicable), **no duration text**
(the row's own height already says "short" — repeating "5 min" in an already-tiny box is
noise, not information). Dashed border keeps a 1dp stroke but tightens to a 2dp-dash/2dp-gap
pitch (from 4/4, both inside the micro-spacing tier below) and a 6dp corner radius (from 12dp,
a separate radius token family — see Spacing Scale) — at 20px tall a 12dp radius would round
away most of the box's visible straight edge, reading as a pill rather than a dashed rectangle.
Vertical padding drops to `0dp` (from the Full-tier's `24dp`/`12dp`) — a real value on the 8-pt
scale (`0` is trivially a multiple of `4`), not a new sub-4dp exception: the label is vertically
centered inside the row's slot via alignment rather than pushed away from the dashed edge by
padding, which is what a 20px-tall box needs anyway (padding plus a `bodySmall` line would
overflow the slot; centering with no padding does not).

**Breaks lose their tap target entirely, at every size, in this surface** — this is a
deliberate behavior change from the current implicit `onTap` (every unresolved chunk,
including breaks, currently opens `ChunkDetailSheet`). Reasoning:
1. It resolves the WCAG touch-target-size problem at the 20px short-break size without adding
   asymmetric "small breaks aren't tappable but long breaks are" behavior a user would have to
   learn the hard way.
2. It extends Phase 23's own established framing — "there is nothing to complete about a
   break, and offering the action would imply the user is meant to work through it" — to its
   natural conclusion: there is also nothing to *inspect* about a break. `ChunkDetailSheet`'s
   content for a break is goal-less rationale text with no actions; losing that tap costs
   nothing a user would miss.

## Scroll-on-open & the rendered vertical range (must-specify #4)

**The rendered range is defined so "now" is always inside it — by construction, not by a
fallback.** Let `firstStart` = the day's first chunk's start minute, `lastEnd` = the last
chunk's end minute. The timeline's total rendered range is:

```
rangeStart = floorToHour(min(nowMinutes, firstStart))
rangeEnd   = ceilToHour(max(nowMinutes, lastEnd))
```

`floorToHour`/`ceilToHour` round to the nearest whole-hour boundary purely for a clean hour-axis
top/bottom (see next section) — they do not change which case applies.

This single formula is the entire answer to "what happens in `PreStart`/`DayComplete`, where
now is outside the day's chunk span": it is never outside the *rendered* span, because the
span's start and end are each a `min`/`max` against `nowMinutes` itself. In `PreStart`,
`nowMinutes < firstStart`, so `rangeStart` extends up to include it — the leading "Free until…"
stretch renders from `now`, not from midnight (an 8am-start day does not force an 8-hour blank
scroll from midnight; the range only reaches as far back as `now` already is). In
`DayComplete`, `nowMinutes > lastEnd`, so `rangeEnd` extends down to include it. In `Active`,
`Overdue`, and `GapBeforeNext`, `nowMinutes` already falls inside `[firstStart, lastEnd]`, so
the formula reduces to the plain `[floorToHour(firstStart), ceilToHour(lastEnd)]` day span.

**Landing position on open: centred (`alignment 0.5`), reusing the exact mechanism Phase
22/24 already validated** — not "upper third" or any new value. Because the now-line is an
overlay computed from a pixel offset rather than a keyed row widget, `Scrollable.ensureVisible`
(which needs a rendered widget's `BuildContext`) no longer applies directly to it. The
one-shot post-frame callback instead computes the target scroll offset arithmetically:

```
targetOffset = ((nowMinutes - rangeStart) * kPixelsPerMinute) - (viewportHeight / 2)
             , clamped to [0, maxScrollExtent]
```

...and calls `_dayScrollController.animateTo(targetOffset, duration: 250ms, curve: Curves.easeOut)`
— same duration/curve Phase 22/24 already used for `ensureVisible`, so the felt motion is
unchanged even though the mechanism computing the destination is new. This replaces **both**
of Phase 24's two centre-on-open flags (`_didCentreLiveRow` for the live row, `_didCentreMarker`
as its PreStart/GapBeforeNext/DayComplete fallback) with **one** flag and **one** code path,
because there is no longer a "does a live row exist" branch to choose between — the now-line
always exists at a computable offset, in every state. This directly answers D-02's flagged
consequence ("auto-scroll-to-now becomes load-bearing, not best-effort") by making the
mechanism unconditional rather than a primary/fallback pair.

The existing one-shot discipline is unchanged: the flag is set synchronously before the
post-frame callback is scheduled, reset on a new `dateYmd` (a new day) and on a `DevClock`
offset jump (Phase 25) exactly as today — a tick must never re-trigger this scroll and drag
the list out from under a reading user.

## CAL-03 — "elapsed time recedes"

**Decision: scroll position only. No new dimming, desaturation, or opacity treatment for
elapsed-but-unresolved time.**

CAL-03's own wording is about the viewport, not about color: "the past does not compete for the
viewport with what is upcoming, and reaching it is a deliberate scroll rather than the default
view." Centre-on-open (previous section) is a complete, literal implementation of that sentence
— on open, everything before "now" is scrolled up off-screen by default, and reaching it costs
a deliberate upward scroll. Reasons for not layering an additional visual treatment on top:

1. **A second opacity system would collide with the existing one.** Resolved chunks
   (completed/skipped) already dim to `~50%` opacity — but that rule is keyed on *resolution
   status*, not clock position, and an `Overdue` chunk (past its window, still unresolved)
   deliberately does **not** dim, per Phase 23's own contract (it renders through the full-weight
   `LiveRowCard`). Adding a second, clock-keyed dimming rule risks stacking or contradicting the
   first — e.g. what happens to a resolved chunk that is also in the future (completed early)?
   Keeping exactly one opacity rule, keyed on resolution only, avoids that ambiguity entirely.
2. **Mood-seeded palette risk.** A low-mood day (mood 1, "Low day") already seeds a duller,
   lower-saturation `ColorScheme`. Stacking a recede-dimming multiplier on top of an
   already-dim palette risks pushing elapsed-row text below usable contrast on exactly the days
   where legibility matters most — a real risk the "justify against the mood-seeded palette"
   prompt is specifically asking to be weighed, and it weighs against adding the treatment.
3. Dan's own words (`26-CONTEXT.md`): *"i think things in the past should have to be scrolled
   to"* — a positional complaint, not a legibility complaint. The scroll mechanic answers it
   directly; a color treatment would be solving a problem he didn't report.

## The time gutter becomes an hour axis (must-specify #6)

**Per-hour, not per-row.** The `52dp` gutter width (`kGutterWidth`, real-browser-verified in
Phase 23 — reused verbatim, not re-derived) stops being a per-`TimelineRowTile` static time
label and becomes a **persistent hour-boundary axis**, because per-row time labels stop making
sense once row height is duration-driven: a 20px short-break row cannot legibly hold a time
label at all, and a 1000px+ empty-gap row would leave its one static label stranded at the very
top of an otherwise-unlabelled void. A y-position-anchored hour axis solves both: it places a
label exactly where that hour actually falls, regardless of what row (if any) occupies that
span.

| Property | Value |
|---|---|
| Column width | `52dp` (`kGutterWidth`, unchanged constant, reused for its new role) |
| Label | Hour only, no minutes — `"9 AM"`, `"12 PM"` (not `"09:00"`) — reads faster at a glance than a full clock-format time, and exact minute precision is what the now-line's own chip is for |
| Label style | `bodySmall` (12px/400), `onSurfaceVariant`, tabular figures — same family as the old gutter text, just repositioned |
| Placement | `Positioned(top: (hourMinutes - rangeStart) * kPixelsPerMinute)`, left-aligned in the reserved 52dp column |
| Hairline | A `1dp` horizontal line in `colorScheme.outlineVariant` at the same y-offset, spanning the remaining content width (right of the 52dp column) — a quiet calendar-style gridline that helps the eye register an hour boundary across a long empty gap |
| Z-order | Painted **behind** row content (chunk cards, free-time rows) and **behind** the now-line — a hairline only becomes visible where it crosses transparent/absent content (free-time gaps, the transparent-fill break rows), never visibly slicing through a filled card |
| Interaction | `IgnorePointer` — purely decorative, like the now-line overlay |

**Per-item time text moves back into the card.** With the per-row gutter gone, `showStartTime`
flips from `false` (its Phase 22 value, chosen specifically because the gutter already showed
it) back to `true` for Full-tier work chunks — the card is now the only place a chunk's exact
start time is legible up close; the hour axis only gives round-hour reference points, not a
specific chunk's minute. Compact-tier work chunks and both break tiers omit the time text per
the density rules above (their own position plus the axis already carries enough information
at that size).

## The live row exception (carried forward, not reopened)

`LiveRowCard`'s "let now break the grid" treatment (`22-UI-SPEC.md`, amended after UAT) is the
**one deliberate, named exception to CAL-01's duration-proportional rule.** Its height stays
content-driven (kicker + title + remaining-time + progress bar + actions + next-line ≈
`200–220px`), not `durationMinutes * kPixelsPerMinute` (which would be `100px` for a typical
25-minute chunk) — it is *supposed* to swell larger than its neighbors; that swelling is the
entire point Dan asked for in the Phase 22 UAT round ("makes it to where I am doesn't just jump
off the page"). Both `Active` and `Overdue` render through this exception (matching
`timeline.dart`'s existing `liveId` derivation, which already treats both as "live" for
`isLive` purposes) — so both are excluded from strict CAL-01 height, consistently.

Practical consequence for the offset math in "Scroll-on-open" above: rows **after** the live
row have their pixel offset pushed down by the live row's actual rendered height, not its
duration-implied slot — the cumulative-offset calculation must read the live row's real
measured height (available post-layout) rather than assuming `durationMinutes * kPixelsPerMinute`
for that one row. This is a pre-existing shape of the problem (Phase 24 already had to reason
about the live row being visually different from its neighbors); it is called out here so the
checker does not flag the live row's size as a CAL-01 violation — it is a documented, locked
exception, not an oversight.

> **Amendment, 2026-08-11 (26-UAT.md G-02, `26-08-PLAN.md`) — `kLiveRowReservedHeight` corrected
> from `240.0` to `232.0`, a real-browser measurement.** The `200–220px` estimate quoted just
> above, and the `240.0` reservation it fed (`26-01-PLAN.md` PD-2), both came from a `flutter
> test` pump — a placeholder-font harness that this codebase has now been bitten by twice
> (`kGutterWidth` `46 -> 75 -> 52`). Re-measured in a real GPU-backed browser (headless Chromium,
> `--use-gl=swiftshader`, 430px viewport, debug build served via `tools/serve-uat.py`),
> screenshot-pixel-counted against `LiveRowCard`'s `primaryContainer` fill:
>
> - **Work variant (the tallest — carries the Complete/Skip action row, so this is what the
>   reservation must be sized against)**: 200px fill + the card's own 24px vertical margin
>   (`EdgeInsets.symmetric(vertical: 12)`, part of its natural `Positioned` layout size since it
>   has no `height:` constraint) = **224px natural height**.
> - **Break variant (sanity-check only — Phase 23's LIVE-01 omits the action row for breaks, so
>   it is shorter)**: 158px fill + 24px margin = **182px natural height**, comfortably under the
>   new reservation.
>
> New value: `224` (measured) `+ 8` (explicit safety margin, absorbing minor cross-renderer/DPI
> anti-aliasing variance — not a full second-line title wrap, which remains a documented residual
> risk) `= 232.0`.
>
> **Honest finding, not just a fix:** the real-browser work-variant figure (224) is close to the
> old harness figure (230) — only 6px apart. Unlike `kGutterWidth` (a width/glyph-advance
> measurement, heavily distorted by the placeholder font), `LiveRowCard`'s height is dominated by
> fixed-size elements (padding, `SizedBox` gaps, button heights) rather than text wrapping, so it
> was far less exposed to the harness's font-metric distortion. The net reservation only dropped
> `240 -> 232` (8px), which shifts every row after the live row up by exactly 8px in both
> variants (confirmed: `liveExtraPx` is `kLiveRowReservedHeight - liveDurationPx`, so the shift is
> constant regardless of which chunk type is live). The `~80px` dead space `26-UAT.md` G-02
> described was observed while a **break** was live — under the corrected value that gap is
> `232 - 182 = 50px`, still visible, because the mechanism reserves for the tallest (work)
> variant by design (Dan's decision, `26-RESEARCH.md` Pitfall 3: a fixed estimate, not two-pass
> measurement). That residual gap during a live break is an accepted structural consequence of
> the single-reservation model, not a defect this plan was scoped to eliminate. Before/after
> evidence: `.planning/phases/26-the-day-has-a-shape/evidence-26-08/`.

## Free / gap rows at proportional height

`LeadingFreeRow` and `GapFreeRow` keep their existing locked copy verbatim (`"Free until
<time>"`, `"Free · <duration>"`) and their existing dotted vertical rule (the rule's painter
already tiles to fill an arbitrary `size.height` — no code change needed there). What changes:

- **Vertical centering, not top alignment.** Every other row type stays top-aligned to its
  duration slot (a chunk's box starts exactly when the activity starts). A free/gap row
  describes the *whole* span, not a single instant, so its label is centered within its full
  proportional height — at `kMinGapMinutes` (10 min → 40px) this is barely different from
  today; at a multi-hour empty stretch it means the label sits roughly where a scrolling user's
  eye naturally lands, rather than being stranded at the very top of a long void.
- **The `10dp` suppression threshold (`kMinGapMinutes`) is unchanged** — gaps shorter than 10
  minutes still render as nothing (a short break already occupies that seam), per the existing
  D-05 rule. This phase does not touch that threshold.

## Card seams

Chunk cards keep their pre-existing `4dp` vertical `margin` (Card) / `4dp` `Container` margin
(break) between rows — **unchanged, not reduced.** At `kPixelsPerMinute = 4.0`, `4dp` of margin
between two time-contiguous chunks (chunk B starts exactly when chunk A ends) reads as roughly
one minute of visual space — small enough, relative to the `10dp`/`40px` `kMinGapMinutes`
threshold at which a real gap earns its own named `GapFreeRow`, that it does not misrepresent a
genuine boundary as a gap. No spacing-scale exception is needed here.

## Spacing Scale

Declared values (multiples of 4 — project-wide 8-point scale, governing **layout rhythm**:
padding, margin, and gaps between elements):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gaps inside the now-line time chip's internal layout; now-line chip vertical padding; inter-row card margin (unchanged from the pre-existing value — see "Card seams") |
| sm | 8px | Now-line chip horizontal padding; hour-axis label inset |
| md | 16px | Inherited outer content inset (`TimelineRowTile`'s existing 16dp, unchanged) |
| lg | 24px | Long-break Full-tier vertical padding (unchanged from `chunk_card.dart`) |
| xl–3xl | 32/48/64px | not used by this phase |

**No layout-spacing exceptions this phase.** Every padding, margin, and gap value above sits on
the 8-pt scale, including `0dp` (Compact-tier break vertical padding — see Row content
density) and the unchanged `4dp` inter-row card margin (see "Card seams").

### Micro-spacing exception tier — stroke, hairline & dash geometry only

The 8-pt scale above governs *layout rhythm* — the distance between one element and the next.
It does not govern *line weight* — how thick a single painted stroke is, which is a different
kind of quantity. Material 3's own divider/outline weights already live below 4dp (a `Divider`'s
default thickness is 1dp), and this codebase already has shipped precedent for a sub-4dp
stroke: Phase 24's now-marker rule (`now_marker.dart`, `24-UI-SPEC.md`, checker-passed) is
`Container(height: 2, ...)` — a 2dp stroke, approved before this phase existed. This tier names
that existing practice as a bounded, closed set rather than leaving sub-4dp values scattered
through the doc as ad-hoc prose.

**Scope — closed set, stroke/hairline/dash geometry only.** Does **not** cover padding, margin,
or any layout gap — those have zero exceptions and stay entirely on the 8-pt scale above.

| Value | Usage |
|-------|-------|
| `1dp` | Compact-tier break dashed border stroke width (unchanged, `_DashedBorderPainter`'s existing default); hour-axis hairline weight (see "Time gutter becomes an hour axis" — a true hairline, deliberately thinner than the now-line so the two never compete) |
| `1.5dp` | Full-tier (long) break dashed border stroke width (unchanged, existing) |
| `2dp` | Now-line stroke weight; Compact-tier break dash length and dash gap (tightened from the existing Full-tier `4dp`/`4dp` pitch) |

**Corner radius is a separate, pre-existing token family in this codebase — not governed by
the 8-pt spacing scale, and not part of the tier above either.** `BorderRadius.circular` values
already range from `2` to `30` across existing, shipped screens with no relationship to spacing
tokens (`chunk_detail_sheet.dart`'s drag handle at `2`, `chunk_card.dart`'s priority chip at
`10`, `breathing_pulse_cta.dart` at `30`). The Compact-tier break's `6dp` corner radius
(reduced from the Full-tier dashed card's existing `12dp`) is judged against that existing,
already-ungoverned radius practice — not against a spacing rule — and is consistent with it.
