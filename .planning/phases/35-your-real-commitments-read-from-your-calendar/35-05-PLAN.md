## The constraint that shapes this plan

**Neither mobile platform can be built here.** `flutter doctor -v` (run during research) reports
`✗ Unable to locate Android SDK`; Xcode has never existed on this Linux box and never will. The
executor can run `flutter analyze` and static checks on this code and nothing else. It cannot run it.

So this plan is deliberately asymmetric:

| Step | Who verifies | With what |
|---|---|---|
| Package legitimacy (Task 1) | the owner | two page loads |
| The code compiles and its read-only surface holds (Task 2) | the executor, on danserver | `flutter analyze` + static greps + a pure-mapping unit test |
| It actually reads a calendar, the permission flow works, a moved recurring occurrence shows at its moved time (Task 3) | **the owner, on his MacBook or an Android phone** | a real build, a real calendar |

**No task in this plan has a `verify` block requiring a mobile build.** Task 3 is a checkpoint
addressed to the owner, not a command the executor pretends to run. Research's Pitfall 1 is explicit
that the recurrence claim is `[CITED: pub.dev]`, not verified — and this repo has a documented record
of confident documentation being contradicted by a real device. Marking CAL-01 done on the strength
of `flutter analyze` would be exactly that mistake.

Decisions implemented: **D-35-03** (the plugin), **D-35-04** (one integration covers both vendors),
**D-35-12** (the mobile branch of the platform switch).

  <action>
`flutter pub add device_calendar_plus` (D-35-03), then `flutter pub get`.

**Alias the plugin import.** The plugin's SDK exports a class it also calls `CalendarSource` — its
`listSources()` returns `List<CalendarSource>` meaning OS-level accounts (iCloud, Google, local),
which is a different concept from this app's `CalendarSource` abstraction. Import the package with a
prefix so both can coexist unambiguously. Research flagged this so it is not discovered mid-task; do
not resolve it by renaming this app's interface, which is referenced across five files by now.

Create `lib/data/calendar/device_calendar_source.dart` implementing `CalendarSource` as a thin
adapter:

- `isAvailable()` — true on iOS and Android, false everywhere else.
- `requestPermission()` — request the **read** level only and map the plugin's
  `CalendarPermissionStatus` onto this app's `CalendarPermissionState`. Map a write-only result to the
  same state as denied: this app never needs write access and must never ask for it (CAL-03, Security
  V4). Requesting a write-capable level the app would never use is itself a trust violation, quite
  apart from any code path.
- `listCalendars()` — map the plugin's `Calendar` (`id`, `name`, `colorHex`, `readOnly`,
  `accountName`, `accountType`, `isPrimary`, `hidden`) onto `CalendarInfo`. Carry `accountName`
  through faithfully; it is what the picker groups by, and grouping by account is how the screen SHOWS
  the owner that his Google account is (or is not) attached, rather than asking him (D-35-04).
- `listEvents(...)` — call the plugin's event listing for the window and the selected calendar ids,
  and map each returned occurrence onto a `CalendarEvent`. Use the occurrence's own instance identity
  as `recurrenceId` so `externalEventId` stays unique per occurrence. The OS resolves recurrence and
  its exceptions before the app ever sees the events; this adapter must not attempt to expand,
  re-expand or correct recurrence itself.

Follow `notification_service.dart`'s platform-branch idiom throughout: an explicit branch with a
trailing comment for every platform, never a silent fallthrough.

**Call only read APIs.** The interface declares no write verb, so nothing downstream can ask for one;
this file is the only place a plugin write API could be reached, and it must not reach one. Do not
call anything that creates, updates or deletes a calendar or an event, for any reason, including
"just to test the permission."

Fill in the mobile branch of `defaultCalendarSource`, replacing 35-03's placeholder: iOS and Android
return `DeviceCalendarSource`; every other platform is unchanged.

**`ios/Runner/Info.plist`** currently has neither calendar usage description. Add both: the iOS 17+
full-access key and its pre-17 counterpart. The strings are user-facing and must describe what Canopy
actually does — read your events so it can schedule around them, and never change them.

**`android/app/src/main/AndroidManifest.xml`**: declare the read-calendar permission. Do **not**
declare the write-calendar permission — its absence is a machine-checkable expression of CAL-03 and
is asserted below.

**The unit test that IS possible here.** `DeviceCalendarSource` cannot run on danserver, but the pure
mapping from plugin-shaped data to this app's uniform shapes can, if it is a separate top-level or
static function taking plain values rather than a method reaching into the plugin singleton. Structure
it that way and test it: a plugin-shaped calendar record maps to the right `CalendarInfo` including
`accountName`; each `CalendarPermissionStatus` maps to the right `CalendarPermissionState`, with
write-only mapping to the same state as denied. This is a genuine test of real logic, and it is
honestly less than device verification — Task 3 is what settles the rest.
  </action>

  <context>
This phase rests on one claim it could not test: that the plugin's event listing returns
**already-expanded occurrences with exceptions applied**, so a recurring meeting whose occurrence you
moved shows at its new time. That claim is `[CITED: pub.dev]` — read off the package's own docs, in a

If it is false, the consequence is not cosmetic. `CommitmentBlock` would have to represent RRULE

  <how-to-verify>
    1. **Build and run on the MacBook** (iOS simulator or device) or an Android phone. This is the step danserver cannot do.
    2. **Grant the permission when iOS/Android asks.** Read the dialog text — that is the `Info.plist` string you are seeing. Does it say something true and unalarming about what Canopy does with your calendar?
    3. **Open Settings → Calendars.** Are your real calendars listed, grouped by account? **Is your Google account there?** If it is, tick it. If it is not, that is an OS Settings matter (the account is not added at OS level) and not a Canopy bug — the screen is showing you the truth either way, which is the whole point of doing it this way rather than asking.
    4. **In your own calendar app — not in Canopy — create a recurring event**, e.g. weekly at 10:00 for four weeks. Then **move ONE occurrence** to a different time (choose "this event only"), and **delete a different single occurrence**.
    5. **⟳ Re-check-in in Canopy. This step is MANDATORY and comes first, before you look at the timeline.** An already-generated day is never regenerated on load — `ScheduleNotifier._loadToday()` reads today's schedule straight from Hive, and the generator only runs at check-in. Judging today's timeline without re-checking-in judges a day built before the calendar was ever read. This exact omission cost a round trip on 2026-08-21 and let a real defect survive three more days.
    6. **Now look.** On the day of the MOVED occurrence, does the commitment appear at its new time, not its original one? On the day of the DELETED occurrence, is it absent? On an ordinary week, does it appear at the base time?
    7. **Turn the permission OFF** in the OS settings, reopen Canopy, and confirm the app is still fully usable: the Commitments screen works, you can add a commitment by hand, and a check-in still produces a day (CAL-04).
    8. **Confirm Canopy changed nothing in your calendar** — the events you created are exactly as you left them (CAL-03).
