# Phase 35 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Read this first:** this is a data/input-layer phase with a small, high-stakes UI surface, not a
new screen family. Every control specified below is an EXISTING Material widget already shipped
somewhere in this codebase (`ListTile`, `CheckboxListTile`, `Card`, `AlertDialog`, `SnackBar`,
`ElevatedButton`/`OutlinedButton`), assembled the way `lib/screens/settings/settings_screen.dart`
and `lib/screens/commitments/commitments_screen.dart` already assemble them. Nothing here invents a
new visual language — see **Sketch Recommendation** at the end for why that means this phase does
not need one, and the one condition under which it should get one anyway.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Flutter/Material 3 app, not a web/shadcn stack; the shadcn gate does not apply |
| Preset | not applicable |
| Component library | Flutter Material 3 widgets only (`ListTile`, `CheckboxListTile`, `Card`, `AlertDialog`, `SnackBar`, `ElevatedButton`, `OutlinedButton`, `TextButton`) — no new dependency for UI |
| Icon library | `Icons.*` (Material Icons), already the app's only icon source |
| Font | Platform default (no custom `TextTheme` anywhere in `main.dart` or `theme_notifier.dart`, confirmed by grep) — do not introduce one for this phase |

**Color system note (read before the Color section below):** this app does not have static brand
colors. `ThemeNotifier.currentTheme` builds `ColorScheme.fromSeed(seedColor: _effectiveSeed())` from
the user's daily mood + time-of-day HSL modulation (`theme_notifier.dart`), so the literal hex behind
`colorScheme.primary` changes hour to hour. The contract below is therefore expressed in **Material 3
role names**, not hex — the fixed thing is *which role* a given element uses, not what that role
currently renders as. This is the correct adaptation of the generic 60/30/10 contract to a
seeded-theme app, not a shortcut around it.

## Spacing Scale

Flutter logical pixels (dp), still 8-point/4-multiple discipline. These are the values already in
use in the screens this phase extends — reused, not invented:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4dp | Icon-to-text gaps, `SizedBox` micro-spacing (e.g. between color swatch and name) |
| sm | 8dp | `Wrap`/`Column` inter-element spacing, `Card` vertical margin |
| card-gap | 12dp | `Card` horizontal margin and internal padding (`commitments_screen.dart`'s existing `_CommitmentRow`) — **approved exception, see below** |
| md | 16dp | Row/section horizontal padding, `ListTile` default content padding, section-heading `Padding` |
| lg | 24dp | Space above/below a full-width CTA card |
| xl | 32dp | Vertical space between the icon and headline in an empty/CTA state (matches `_emptyState()`) |

Exceptions: **`card-gap` (12dp)**, used for `Card` horizontal margin and internal padding. 12 is a
multiple of 4 but is not in the standard 4/8/16/24/32/48/64 set. It is named as an exception rather
than mapped onto `sm`(8dp)/`md`(16dp) because it is not a value this phase introduces — it is
`commitments_screen.dart`'s existing, already-shipped `_CommitmentRow` `Card` margin
(`EdgeInsets.symmetric(horizontal: 12, vertical: 4)`), which the new imported-row treatment (Screen &
State Inventory §3) lands inside unchanged. Remapping the table's number to 8 or 16 would describe a
value the actual code does not use; naming it as an approved exception keeps the document honest
about what's on screen.

**Tap targets — the PresetChipGrid trap does not apply here, by construction.** This phase must not
render a chip-like control for the calendar picker. `CheckboxListTile` and `ListTile` both default to
Material's full-width row with a **56dp minimum height**, clearing the 48dp guideline with margin —
unlike `FilterChip`'s measured 34dp (`preset_chip_grid.dart`, the known open issue). If any future
revision of this spec proposes a chip anywhere, it must state the resulting tap-target height
explicitly, per the standing rule for this repo.

## Typography

This app inherits Flutter's default Material 3 `TextTheme` wholesale — confirmed by grep, no
`TextTheme(...)` override exists anywhere. The generic "3-4 sizes, 2 weights" web contract is
translated into **which M3 role each element uses**, not a hand-picked size/weight pair, because
picking new numbers here would silently diverge from every other screen in the app.

| Role | M3 TextTheme member | Size/Line-height (M3 default) | Weight | Usage in this phase |
|------|---------------------|-------------------------------|--------|----------------------|
| Section heading | `bodyMedium` + explicit `FontWeight.w600` | 14sp / 20sp (1.43) | 600 | "Calendar" section heading in Settings; account-group headers in the calendar picker |
| Row title | `titleMedium` | 16sp / 24sp (1.5) | 500 (M3 default) | Calendar name, commitment name |
| Body | `bodyMedium` | 14sp / 20sp (1.43) | 400 (M3 default) | CTA card explanatory copy, dialog body text |
| Secondary/caption | `bodySmall` | 12sp / 16sp (1.33) | 400 (M3 default) | Row subtitles (sync status, account name, skip reasons) |

No new size is introduced. Exceptions: **three weight values (400/500/600) appear across this
phase's surfaces, exceeding the 2-weight contract.** None of the three is introduced by this phase —
all three are already on screen, today, in the two exact files this phase extends:

- **600** — `settings_screen.dart`'s existing section headings ("Notifications" `:254`, "Data" `:392`,
  "Reviews" `:422`, "Debug" `:443`) are all `bodyMedium.copyWith(fontWeight: FontWeight.w600)`. The new
  "Calendar" heading (Screen & State Inventory §1) matches this shipped, four-call-site pattern rather
  than inventing a fifth, differently-weighted heading.
- **500** — `commitments_screen.dart`'s row titles (the empty-state heading `:129`, `_CommitmentRow`'s
  commitment name `:247`) are bare `titleMedium`, whose Material 3 default weight is `w500`. The new
  calendar-picker's row titles use the same unmodified `titleMedium`.
- **400** — `bodyMedium`/`bodySmall` unmodified, the M3 default for body copy and captions everywhere
  in this app already.

Normalising to two weights (e.g. dropping the new "Calendar" heading's `w600`, or bumping row titles
to `600`) would make that one heading, or that one list's row titles, render at a visibly different
weight than every other Settings heading directly above and below it, or every other row title
elsewhere in the app — a real, visible regression traded for a document-internal rule. As with
`card-gap` above, the honest fix is to name the exception, not to narrate three values as two.

## Color

Expressed as M3 roles, per the Design System note above.

| Role | M3 role used | Usage |
|------|-------------|-------|
| Dominant (~60%) | `colorScheme.surface` | Screen background (`Scaffold`), `ListView` background |
| Secondary (~30%) | Card/`ListTile` default surface tones (unspecified explicitly anywhere else in this app — inherited from `Card`/`ListTile` defaults, not overridden) | CTA cards, calendar-picker rows, dialogs |
| Accent (~10%) | `colorScheme.primary` | **Reserved for, and only for:** the primary CTA button ("Allow calendar access" / "Add calendar URL"), the checked fill of a selected calendar's `CheckboxListTile`. Nothing else in this phase's surfaces uses `colorScheme.primary`. |
| Destructive/error | `colorScheme.error` | **Reserved for, and only for:** the "sync failed" status line/icon (a genuine failure, not a benign state) and the "Remove" button text in the remove-ICS-subscription confirmation dialog (matches `_confirm()`'s existing pattern in `settings_screen.dart`/`commitments_screen.dart`) |
| Neutral/informational | `colorScheme.onSurfaceVariant`, `colorScheme.outline` | Permission-denied explanatory card (this is an OS state, not an app error — do not tint it with `colorScheme.error`), the "imported from calendar" marker icon, section-heading text color inherited from `bodyMedium` default |

**Explicit non-use, stated because this repo has a documented history of "error" being reached for
reflexively:** the permission-DENIED state is informational, not an error — the user did nothing
wrong and the app is not broken. It uses a neutral outlined `Card`, never `colorScheme.errorContainer`
or `colorScheme.error`. Only an actual sync failure (a real operation that actually failed) earns the
error role, matching `chunk_card.dart`'s own documented rule ("never the error slot" for anything
that isn't a real error).

The color swatch circle on an imported commitment row (`_CommitmentRow`'s existing 16dp circle) keeps
using the commitment's own stored `color` hex field — untouched by this phase, unrelated to theme
accent.

## Screen & State Inventory

This is the part a generic web UI-SPEC template has no slot for, and the part the executor actually
needs — the four scoped surfaces, concretely.

### 1. Settings entry point (new row, existing screen)

`lib/screens/settings/settings_screen.dart` gains one new section, **"Calendar,"** placed after the
existing "Notifications" section (before "Data") — same section-heading treatment
(`Padding(16,16,16,8)` + `bodyMedium.copyWith(fontWeight: FontWeight.w600)`) as the existing sections
(Typography's named exception above). One `ListTile`:
`leading: Icon(Icons.calendar_month)`, `title: Text('Calendars')`, `subtitle`: per the Copywriting
Contract's "Settings entry row" rows above, `trailing: Icon(Icons.chevron_right)`, `onTap` pushes the
new Calendar settings screen (route suggestion: `/settings/calendars`, matching the existing
`/settings/past-reviews` pattern).

### 2. Calendar settings screen (new screen) — CAL-02 + CAL-04

New `AppBar(title: Text('Calendars'))`. Body branches on platform and state — **mobile
(iOS/Android) uses the device-calendar path; desktop/web uses the ICS-URL path.** Research's own
architecture note (Pattern 1: "platform selection happens once, at construction") is read as *one
active source type per platform*, not a simultaneous multi-source UI — do not build a combined
picker; branch the whole screen body by platform.

**Mobile body, by permission state:**

| State | Rendering |
|-------|-----------|
| Not yet requested | Centered CTA card (icon `Icons.calendar_month` 48dp, `onSurfaceVariant`; headline + body per Copywriting Contract; `ElevatedButton` "Allow calendar access") |
| Requesting (in flight) | Centered `CircularProgressIndicator`, no other content — same idiom as the existing `_exporting` spinner in `settings_screen.dart` |
| Granted, ≥1 calendar | `ListView` grouped by `accountName`: group header (section-heading style, e.g. "you@gmail.com") → one `CheckboxListTile` per calendar under it (`secondary: Container(16dp circle, calendar.color)`, `title: Text(calendar.name, maxLines: 1, overflow: TextOverflow.ellipsis)`, `value:` current selection, `onChanged:` persists selection). Selection persists immediately per toggle — no separate "Save" step, matching every other settings toggle in this app. |
| Granted, 0 calendars found | Empty state per Copywriting Contract ("No calendars found on this device") |
| Denied / restricted | Neutral outlined `Card` (NOT `errorContainer` — see Color contract) with headline + body per Copywriting Contract, `OutlinedButton` "Open Settings" |

**Desktop/web body, by ICS configuration state:**

| State | Rendering |
|-------|-----------|
| No URL configured | Centered CTA card, same shape as mobile's, copy swapped per "desktop/web" rows in Copywriting Contract, `ElevatedButton` "Add calendar URL" opens the add-URL form (via `showAdaptiveFormModal`, the existing modal helper used by `CommitmentFormSheet`) |
| ≥1 URL configured | `ListView`: one `ListTile` per subscribed URL — `leading: Icon(Icons.link)`, `title:` calendar's own name once fetched (fallback: the URL, truncated with ellipsis), `trailing: IconButton(Icons.delete_outline)` → the remove-confirmation dialog from the Copywriting Contract. A persistent row below the list, same "Add calendar URL" affordance as an `OutlinedButton.icon` this time (secondary action once at least one exists). |
| Add-URL form validation failure | Inline `TextFormField.errorText`: "Couldn't read that calendar. Check the URL and try again." — standard Flutter form-validation idiom, no new pattern |

**Persistent footer, both platforms, whenever at least one source is configured (device permission
granted OR ≥1 ICS URL):** a `bodySmall`, `onSurfaceVariant` status line under the list — sync status
copy per the Copywriting Contract, with the skipped-events disclosure line beneath it when the last
sync skipped anything. Tapping the disclosure opens a simple `ListView` inside a modal sheet: one row
per skipped event, `title:` the event's own title, `subtitle:` its skip reason string.

### 3. Distinguishing an imported commitment — Commitments screen (existing screen, extended)

`lib/screens/commitments/commitments_screen.dart`:

- **AppBar gains one action icon**: `Icon(Icons.calendar_month_outlined)`, tooltip "Calendar
  settings", navigates to the Calendar settings screen — persistent one-tap discoverability without
  cluttering the populated list.
- **`_emptyState()` gains one element**: below the existing "Add your regular jobs, classes, or
  appointments" body text, `SizedBox(height: 16)` then `OutlinedButton.icon(Icons.calendar_month,
  Text('Import from your calendar'))`, same navigation target. Nothing else in `_emptyState()`
  changes.
- **`_CommitmentRow` gains an imported-source treatment**, gated on `block.isFromCalendar == true`
  (the new `HiveField(8)` from RESEARCH.md Pattern 4):
  - A small `Icon(Icons.calendar_today_outlined, size: 14, color: colorScheme.onSurfaceVariant)`
    renders inline after the existing color-swatch circle and before the name/subtitle `Column` —
    `Semantics(label: 'Imported from your calendar')` for screen readers, since it carries meaning
    with no visible text.
  - The trailing edit/delete affordances (both the always-visible mobile `IconButton` and the
    desktop hover row) are **suppressed entirely** for an imported row — editing happens in the
    user's calendar app, and deleting would be silently undone by the next upsert-by-`externalEventId`
    sync (Pattern 4), which is a worse UX than not offering the control. No trailing icon replaces
    them; the row simply has no trailing affordance, keeping the layout honest about what's possible.
  - Tapping an imported row does **not** open `CommitmentFormSheet`. It opens a small read-only
    bottom sheet/dialog: title = the commitment's name, body = time range + copy from the
    Copywriting Contract's "Imported-commitment read-only sheet," and one `TextButton` "Manage
    calendars" navigating to the Calendar settings screen.
  - Hand-entered rows (`isFromCalendar == false`, the default) are **completely unchanged** — same
    edit-on-tap, same edit/delete affordances as today.

### 4. Distinguishing an imported commitment — Today timeline (existing widget, extended minimally)

`lib/screens/schedule/widgets/chunk_card.dart` already has a commitment/goal distinction
(`isCommitment = chunk.commitmentId != null`) and an established, documented rule: *"the CONTENT
degrades [by density tier], never the box."* This phase extends that rule rather than inventing a
new one:

- At `detailed`/`full` density, a work chunk anchored to an imported commitment renders the same
  14dp `Icons.calendar_today_outlined` glyph (identical color/semantics to the Commitments-screen
  treatment) inline next to the chunk's title text, space permitting.
- At `compact` density, the glyph is **omitted** — title-only compact rows do not grow to
  accommodate it, per the file's own no-widget-ever-floors-or-ceilings-its-box rule. The full
  imported/hand-entered distinction remains reachable by tapping through to `ChunkDetailSheet`,
  which also carries the glyph + the same "Imported from your calendar" label in its header.
- This requires plumbing `CommitmentBlock.isFromCalendar` through to `ScheduledChunk` (or resolving
  it via a lookup at render time) — a data-flow decision for planning, not a visual one; the visual
  contract above is what that plumbing must ultimately paint.

### 5. Platform degradation (`NullCalendarSource`) — no dedicated screen state

There is no platform where the app reaches a state with no designed UI. `NullCalendarSource` is the
**absence of configuration**, not a distinct mode:

- On mobile, before permission is granted (or after it's denied), the states in the table above
  ("Not yet requested" / "Denied") already cover it — those ARE what "no device calendar access"
  looks like.
- On desktop/web, before any ICS URL is added, the "No URL configured" CTA state already covers it.
- **Do not build a fourth, separate "calendar unavailable" screen.** If a future platform genuinely
  has neither mechanism, it falls through to the "not yet requested"/"no URL configured" CTA
  depending on which branch the platform check selects — the CTA's own copy ("Canopy can show every
  calendar...") is honest either way since the button leads to the OS permission dialog or the URL
  form respectively, and CAL-04's guarantee (hand-entered commitments fully usable) holds regardless
  because nothing on the Commitments screen or Today timeline requires a calendar source to exist.

## Sketch Recommendation

**No sketch required for this phase.** Every control specified above is an existing, already-shipped
Material widget assembled the way this app already assembles it: `ListTile`/`CheckboxListTile` rows
(`settings_screen.dart`), a centered icon+headline+body CTA card (`commitments_screen.dart`'s
`_emptyState()`), `AlertDialog` confirmation (`_confirm()`, used identically in two screens already),
`SnackBar` for a background-operation failure (`_snack()`), and a 14dp neutral status glyph following
`chunk_card.dart`'s own documented density-degradation rule. None of this is a new visual language —
it is the existing one, applied to a new domain.

**The one condition under which this should still get a sketch:** if, once the calendar-picker screen
and the permission CTA card are actually assembled and rendered (not just read about), they do not
visually cohere as one screen — this repo's own documented lesson from Phase 32 is that "locally
provable, wrong at the altitude a human sees" is a real failure mode, and a prose spec passing a
checker is not evidence against it. If that happens, stop and route through `/gsd-sketch` (whole
screen, served on the tailnet) rather than iterating blind on constants — do not repeat Phase 32's
mistake of treating a tight crop of one element as proof the full screen reads correctly.
