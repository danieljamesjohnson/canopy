<objective>
Make the always-safe fallback real and give the calendar configuration somewhere to live: the
platform switch, the `NullCalendarSource` guarantee, and three additive `AppSettings` fields the
picker screen will read in the next wave.

Purpose: CAL-04 says a platform with no calendar access still gives a fully usable app. That is the
requirement most likely to be assumed rather than proven, because on the machine this is developed on
it is *always* true — there is no device calendar here at all. So it gets its own tests.

Output: `defaultCalendarSource`'s real platform branches, `NullCalendarSource`'s proof, and the
persisted selection/feed/last-sync state.

**Verifiable entirely on danserver** — `flutter analyze` plus two new test files. Nothing in this plan
needs the owner.

Decisions implemented here: **D-35-10** (permission state is queried live, never cached),
**D-35-12** (one active source type per platform). Both are planner calls recorded in 35-01.
</objective>

queried live when the settings screen builds, in plan 35-04.
