  <name>Task 1: Rule the all-day question — the one genuinely unresolved thing in this phase (D-35-06)</name>

  <decision>When your calendar has an all-day entry, does Canopy block that whole day, or leave it alone and tell you it did?</decision>

  <context>
This is the single item both research (Assumption A3) and the UI design contract refused to settle
on their own, and it is surfaced here rather than quietly decided because the failure mode in one
direction is severe.

**Why it matters.** All-day entries are extremely common and mostly low-signal: birthdays, public
holidays, "Out of Office" banners, a subscribed sports-team calendar. An all-day entry imported as a
blocking commitment consumes the entire day's window, which given the generator's modest per-mood
chunk counts means the schedule for that day comes back essentially empty. The user would see a day
with nothing in it and no explanation — the exact class of surprise that makes someone stop trusting
the app.

**Why it isn't obvious.** The other direction has a real cost too: a genuine all-day out-of-office
would be ignored, and Canopy would happily schedule a full day of work while you are away.

**Nothing in the calendar data distinguishes the two.** "Birthday: Sam" and "Out of office" are the
same shape of record. No field separates a banner from a real block — which is why this is a product
judgment and not a mapping detail.

The UI-SPEC has already locked the copy for the recommended default ("All-day — not imported
automatically" in the skipped-events list), so the surface is built either way; only the mapper's
behaviour changes.
  </context>

  <options>
    <option id="skip-and-disclose">
      <name>A — Do not import all-day entries as blocking commitments; disclose each one in the skipped list</name>
      <pros>Research's recommendation and the UI-SPEC's already-locked copy. The day stays schedulable, and the user can see exactly which entries were passed over and why. Fails in the recoverable direction.</pros>

**Read the window from settings — do not hardcode `08:00–18:00`.** The span must resolve from the same
settings value the rest of the app uses (find it; `app_settings.dart` is the likely home). A test that
asserts the literal pair `480`/`1080` would pass for a user whose window differs and could never fail —
that is this repo's single most-repeated defect (`CLAUDE.md`, "Assertions that cannot fail"). Assert
the relationship to the settings value, and mutation-prove it by changing the configured window and
watching the expectation move with it.

**Why not `0..1440`, recorded so it is not "corrected" later:** see `35-DECISIONS.md`. The owner's
question showed `08:00–18:00`; a literal all-day block would also hand `schedule_generator.dart` a

explicitly flagged for owner confirmation in `35-06`'s UAT** — implement it, and do not record it in
the SUMMARY as though the owner stated it.

**Cancelled.** An event whose `status` is cancelled is skipped with `SkipReason.cancelled`. A
tentative event imports normally. **Do not attempt per-attendee decline filtering** — research
(Assumption A2) found no reliable "this attendee is the device owner" field, and filtering the wrong
attendee's decline would either hide a real commitment or show one the user does not have. That is a
stretch goal for a later phase, gated on device verification, and is deliberately out of this plan.

**Too short, zero duration, and no end time.** Route all three through the EXISTING
`commitmentWindowTooShort` gate — it is already enforced on the hand-entry form and on onboarding, and
a calendar-sourced block that bypassed it would be the only path in the app capable of creating a
commitment that renders as a phantom with zero chunks. For an event with no end time, follow RFC
5545's own convention and treat it as a point in time: zero duration, therefore too short, therefore
skipped with `SkipReason.tooShort`. Every gated event lands in `skipped` with the UI-SPEC's "Too
short to schedule" copy — visible, never silent.

**Multi-day and midnight-crossing.** Split an event spanning more than one local calendar day into
one slice per day it touches, each clipped to that day's `0..1440` window, then run EVERY slice back
through `commitmentWindowTooShort`. A three-day conference becomes three one-off blocks; an
11pm–2am meeting becomes an 11pm–midnight slice (60 minutes, imports) and a midnight–2am slice (120
minutes, imports) rather than one inverted block. **This is not a fix for the overnight-commitment
scope boundary and must not become one** — Canopy has no midnight-crossing commitment support
anywhere, deliberately, by the owner's 2026-07-03 ruling. Clipping at the day boundary is how the
importer stays inside that boundary instead of reopening it. No block may ever be persisted with its
end at or before its start; `commitmentWindowTooShort` already rejects that shape and is the gate.

Each slice needs its own `externalEventId` suffix so the per-day blocks do not collide on upsert —
extend the key with the slice's own date.

**Foreign timezone.** An event carrying an IANA zone different from the device's must still map to
the device's LOCAL wall-clock minutes, via the same `tz.TZDateTime.from(..., tz.local)` conversion
the tracer established. Do not special-case it; verify it.

**The three DTSTART forms — WINDOWS.md entry 2, folded into this plan by the owner on 2026-09-15.**
This is the highest-value correctness work in the plan; treat it as such rather than as an edge case.

The tracer (`35-01`) proved exactly ONE form: `DTSTART:20260302T140000Z`, UTC-suffixed. RFC 5545
permits three, and **the one the tracer proved is the one a real Google Calendar feed is least likely
to send.** A Google feed emits `DTSTART;TZID=America/Chicago:20260302T140000` with a matching
`VTIMEZONE` block. So the tracer is currently proven against a shape the owner's own calendar will
probably never produce.

| Form | Example | Meaning | Status after 35-01 |
|---|---|---|---|
| UTC | `DTSTART:...T140000Z` | absolute instant | ✅ proven |
| Zoned | `DTSTART;TZID=America/Chicago:...T140000` + `VTIMEZONE` | instant in a named zone | ❌ **unproven — the Google form** |
| Floating | `DTSTART:...T140000` (no `Z`, no TZID) | "2pm wherever the viewer is" | ❌ **unproven — falls through to Dart system-local** |

**The defect, precisely.** `ics_calendar_source.dart` relies on `enough_icalendar` returning a
`DateTime`. For a non-`Z` value that `DateTime` comes back with `isUtc == false`, constructed against
**the machine's real system timezone** — not the app's injected `tz.local`. Every other date path in
this app routes through `tz.local` (that is what `notification_service.dart:30-55` establishes), so
this is the one place that silently disagrees with the rest of the app.

**Required behaviour:**
- **Zoned:** resolve through the named zone, then convert to local wall-clock via the same
  `tz.TZDateTime.from(..., tz.local)` seam. Do not add a second conversion path.
- **Floating:** interpret the literal wall-clock reading against **`tz.local`**, never against
  `DateTime`'s system-local constructor. Per RFC 5545 a floating time means "this clock reading, in
  the viewer's zone" — so 14:00 floating must yield `startMinutes == 840` under *any* `tz.local`.

**Why this cannot be tested casually, and the trap to avoid.** danserver's system timezone is **UTC**,
which makes `tz.local`-correct and system-local-correct produce **identical numbers here** for the
floating case. A test written without explicitly setting a non-UTC `tz.local` will pass on this
machine whether or not the bug is fixed, and fail on the owner's phone. **That is the SEED-006 trap
exactly** — 3248 green lines that only ever exercised the one input where the bug could not fire. Set
`tz.local` to a non-UTC zone in these tests, assert bare literals, and mutation-prove both.

**If either form cannot be made correct within this plan, leave WINDOWS.md entry 2 OPEN and say so in
the SUMMARY.** Do not run `gsd-tools windows fixed 2` on the strength of having investigated it.

**Overlap.** Import overlapping events exactly as they are (D-35-09). The calendar genuinely has the
user double-booked, and saying so is more honest than merging into a union window (which loses
per-meeting identity) or silently dropping one. No overlap detection code is added to the mapper.
The generator's tolerance is pinned in Task 3.
