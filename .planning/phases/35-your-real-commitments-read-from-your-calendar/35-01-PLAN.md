## Why the ICS path is the tracer, not the device path

The orchestrator's constraint is load-bearing here, so it is stated in the plan rather than left in
the brief: **neither mobile platform can be built on danserver.** `flutter doctor -v` (run during
research) reports `✗ Unable to locate Android SDK`, and Xcode has never existed on this Linux box.
The `device_calendar_plus` path therefore cannot be executed by the agent at any point — its first
real signal is the owner's MacBook.

The ICS path can be executed here, today, by `flutter test`, and later exercised by the owner in a
browser over the tailnet, which is how he actually tests this app. So the tracer lands there. The
device source is plan 05, and its acceptance is explicitly the owner's, not the executor's.

**The pages were looked at rather than reasoned about, and it turned up something this plan had
wrong.** `getInstances()` — the occurrence-expansion API D-35-02's architecture depends on — belongs
to **`rrule`** (JonasWanke), a dedicated RRULE library, **not** to `enough_icalendar`. So the choice
was never "one SUS package vs. a parser that cannot expand", which is how this plan framed it.

The decisive numbers, all read off pub.dev/GitHub on 2026-09-14:
- `rrule` — **128k weekly downloads**, 94 likes, 58 stars, verified publisher `wanke.dev`, actively maintained.
- `enough_icalendar` — 7.55k weekly downloads, verified publisher `enough.de`, last release 12 months ago.
- `firstfloor_calendar` — **52 weekly downloads, 2 stars, 0 forks**, and the ownership mismatch research
  flagged is **REAL and still present**: pub.dev publisher is `firstfloorsoftware.com`, the GitHub repo
  owner is an individual, `kozw`. It was re-checked rather than inherited, and it survived the re-check.

**Three costs this ruling carries into Task 2 — do not rediscover them mid-task:**

1. **Two dependencies, and we own the seam.** `enough_icalendar` parses the `.ics` into a VEVENT model;
   `rrule` expands the RRULE. Nothing joins them for us.
2. **`rrule` requires `isUtc: true` on every `DateTime` handed to it.** Its README: *"rrule doesn't care
   about any time-zone-related stuff. All supplied `DateTime`s must have `isUtc` set to `true`."* This
   collides directly with `CommitmentBlock`'s **local wall-clock** minutes-from-midnight. **That is the
   SEED-006 trap's exact shape** — now a named boundary instead of a latent one. Per D-35-08 the test
   across that seam must set `tz.local` explicitly; a fixture that passes only because danserver's
   system zone is UTC proves nothing. This also makes Task 2's doc-comment fix
   (`commitment_block.dart:29,33`, which wrongly claims UTC) **more** load-bearing, not less — `rrule`
   genuinely does want UTC, so a stale comment asserting the field already is UTC is now actively
   dangerous.
3. **Neither package handles `EXDATE` / `RDATE` / `RECURRENCE-ID`.** Neither did `firstfloor_calendar`
   in any documented way, so this is not a regression against the alternative — but this plan's
   `must_haves` assert MOVED-occurrence and EXDATE behaviour, so that logic is now **ours to write**.
   If it cannot be delivered in this plan, say so in the SUMMARY and scope it explicitly; do not let
   the `must_have` quietly pass on a package capability that does not exist.

**`rrule`'s own stated limits**, so nobody rediscovers them: `WKST` custom week starts unsupported
(Monday only); no leap seconds; years outside 0–9999.
