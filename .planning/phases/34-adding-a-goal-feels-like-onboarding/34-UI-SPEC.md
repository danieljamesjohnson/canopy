## Spacing Scale

This project does not declare a formal 8-point token file; the values below are what the two source
widgets (`_ChipCloud`, `_QuickPickSection`) already ship, and where they **agree** the agreed value is
the contract (per the hard constraint: reuse before inventing).

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gap inside a chip; gap between a `GoalCard`'s name row and its secondary (budget) line |
| sm | 8px | `Wrap(spacing: 8, runSpacing: 8)` between preset chips — **identical in both source widgets, not invented here** |
| md | 12px | Row/card internal padding (`_DoorTile`, `GoalCard` content padding, restoratives `_RestorativeRow`) |
| md+ | 16px | Sheet/section horizontal padding (`_QuickPickSection`'s `EdgeInsets.fromLTRB(16, 12, 16, 8)`, `GoalCard` margin) |
| lg | 24px | `GoalFormSheet`'s own outer padding (`EdgeInsets.fromLTRB(24,24,24,…)`) — the new preset-picker sheet reuses this exact figure so the two sheets a user flips between (picker → form) do not visibly shift margins |

### Exception: `md = 12px` is a documented project token, not a gap

**Stated explicitly because the UI checker BLOCKED on it (2026-09-08)** — 12 is a multiple of 4 but
is not a member of the standard `{4, 8, 16, 24, 32, 48, 64}` set the checker enforces.

**It is nevertheless the correct value here, and the deviation is Canopy's, not this phase's.**
12px is this project's established internal-padding token and pre-dates this phase by many months.
Measured on 2026-09-08: **18 `EdgeInsets` sites across 8+ files**, including all three widgets this
phase touches or extracts from:

- `add_kind_fork.dart:230` — `EdgeInsets.symmetric(horizontal: 12, vertical: 12)` (the fork's own
  door tiles, which the preset row sits beneath)
- `restoratives_screen.dart:361,367` — the `_RestorativeRow` margin and padding, i.e. one of the two
  widgets being merged into the shared preset chip
- `goals_screen.dart:248`, `chunk_card.dart:318`, `commitments_screen.dart:223,229`, and others

**Why it is not "fixed" to 8 or 16.** Doing so would change the rendered padding of three already
shipped widgets to satisfy a token list, in a phase whose entire premise is *extract and reuse, do
not invent*. The hard constraint on this phase is that where the source widgets already agree, the
shipped value IS the contract. They agree on 12. Changing it would also put a visual diff in front
of the owner that has nothing to do with what he asked for — and this project has been burned
specifically by visual changes that a green suite thought were free.

**Standing decision, not a one-off waiver:** treat 12px as an accepted Canopy spacing token for
row/card internal padding. A future phase that wants to normalise it should do so deliberately,
across all 18 sites at once, with the owner looking at the result — not incidentally.

No **new** spacing value is introduced by this phase.

## UI Considerations

**Probe run 2026-09-08** over 7 named surfaces (E1 sheet, E2 grid, E3 chip, E4 add-your-own,
E5 just-added list, E6 budget line, E7 Done): **50 applicable considerations**, resolved below.
The researcher's original 7-row table is preserved and extended — the probe's value here was one
genuinely missing case (`error` under one-tap creation), not the other 42.

### The one the probe caught that matters — read this before planning

| Category | Element(s) | Status | Resolution |
|----------|------------|--------|------------|
| **error** | **E3 preset chip — save fails after the chip has already vanished** | ✅ **resolved (explicit)** | **This risk is created by ruling (a) and exists on no other add path.** Decision 4 requires the chip to disappear *synchronously, same frame*, not gated on the async save — that is what closes the double-tap race. But `GoalsNotifier` persists to Hive, and Hive writes **can** fail: `goal_form_sheet.dart:113` already ships `Could not save goal. Please try again.` for exactly this. On the form path a failure is visible because the user is still sitting on the form. **On the chip path the user has already moved on, and the optimistic UI has already lied to them** — chip gone, card shown, nothing saved. **Required behaviour:** on a failed create, restore the chip to the grid, remove its "Just added" card, and surface the existing failure copy in a `SnackBar`. A silent swallow here reproduces the "help" defect in a worse form — a goal the user believes exists and does not. |

**Why this was worth the probe.** Every other UI-SPEC row describes what the user sees when things
work. This is the one where (a)'s speed — the thing the owner chose it for — is also what hides the
failure. It is cheap to get right and invisible when got wrong.

## Component & Interaction Contract

This is the load-bearing section for this phase — the template's generic fields above don't carry
enough resolution for a reuse-and-extract job with a ruled interaction model. Every numbered decision
below answers one of `34-CONTEXT.md`'s named open questions.

### Visual hierarchy — the focal point, stated rather than implied

*(Added 2026-09-08 in response to the UI checker's non-blocking Dimension-2 FLAG: the flow order
below implied a hierarchy but never declared one, leaving an executor to infer it from step
ordering.)*

**The preset grid is the primary visual anchor of `GoalPresetPickerSheet`** — it is the thing the
owner asked for ("the pre chosen options"), it occupies the largest area, and it is what the eye
should land on when the sheet opens. Everything else is subordinate to it:

| Rank | Element | Weight |
|---|---|---|
| 1 | **The preset chip grid** | Primary. Largest area, first thing below the title, full accent-eligible chip treatment. |
| 2 | "Add your own" row | Secondary. Present and obvious, but must not compete with the grid — it is the *escape hatch*, not the default action. It carries the only accent icon in the sheet, which is enough to find it without enlarging it. |
| 3 | "Just added" cards | Tertiary. Confirmation/receipt, not a call to action. They appear below the fold of the primary choice and read as a running tally of what just happened. |
| 4 | "Done" | Terminal. An accent button, but positioned as an exit rather than an objective — nothing about the sheet should suggest you must press it before the goals are real. They are real the moment the chip is tapped. |

**The one hierarchy inversion to avoid:** if "Just added" grows tall enough to push the preset grid
off screen, the sheet stops reading as "pick from these options" and starts reading as a list
manager. Decision 5's re-visit rules govern this; the executor should treat "the grid is still
visible after adding several goals" as part of the contract, not a nicety.

### The flow, end to end

1. Goals screen → existing `Add goal` button (unchanged) → existing `showAddKindFork` dialog
   (unchanged: "What are you adding?" / two doors).
2. Choosing **"Something that restores you"** → unchanged, `showRestorativeQuickAdd` — this phase
   does not touch the restorative door.
3. Choosing **"Something to make time for"** → **changed.** Today this pops the fork and opens
   `GoalFormSheet` directly (blank form). It now instead opens a **new sheet** — call it
   `GoalPresetPickerSheet` for this document; naming is planner/executor discretion — via the same
   `showAdaptiveFormModal` call `_openAddSheet` already uses for the form (same bottom-sheet-on-mobile
   / dialog-on-desktop chrome, same 720dp breakpoint, same drag handle convention as `GoalFormSheet`).
4. `GoalPresetPickerSheet` shows, top to bottom: the sheet title, the "Common" preset grid (if any
   presets remain unclaimed), the "Add your own" row, then a "Just added" list of any goals created
   in this visit, then "Done." This order is the sketch 006 variant A order (`chipgrid` → `qadd` →
   `outA`) and is kept verbatim rather than re-argued.
5. Tapping an unclaimed preset chip creates the goal **immediately, no interruption** (ruling (a)) and
   the chip disappears from the grid; a `GoalCard` for the new goal appears in "Just added" below.
   The sheet **stays open** — the user can tap several chips in one visit, which is the literal
   "feels like onboarding" ask (onboarding lays down a whole slate before moving on).
6. Tapping "Add your own" **pops this sheet** and opens `GoalFormSheet` (blank, create mode) — the
   exact call `_openAddSheet` makes today. It does not stack a second modal on top of the first; this
   codebase's established pattern is one modal at a time (the fork itself pops before opening the next
   sheet).
7. Tapping a row in "Just added" pops this sheet and opens `GoalFormSheet` in **edit** mode for that
   goal — reusing `_openEditSheet`'s existing call, giving "tapping the row opens the full form"
   (the CONTEXT.md mitigation) for free from an already-shipped, already-tested code path.
8. "Done" pops the sheet, returning to the Goals screen, where every goal created this visit now
   renders through the standard `GoalCard` in its normal ranked position.

### Decision 1 — where the mitigation actually lives (hard constraint #2)

**No new widget is needed for "the created goal row states its budget on its face."** `GoalCard`
already renders it: `_secondaryLine()` returns `'${weeklyHourBudget!.toStringAsFixed(1)} hrs/week'`
for any `timeTarget` goal with a non-null budget, at `bodySmall`, directly under the name, 4dp gap
above and below (`goal_card.dart:176-191, 326-329`). Since every preset-created goal is
`GoalType.timeTarget` with `weeklyHourBudget: 3.0` (the sketch's own assumed values — type, budget,
priority — are fixed across all 8 presets, not per-preset), this line **always renders** for a
freshly created goal. The mitigation is satisfied by reusing a widget that already does the right
thing, not by building a new one.

- **Placement:** directly below the goal name, above the type/valence chip row.
- **Type scale:** `bodySmall` (12px/400).
- **Colour role:** the theme's default `bodySmall` colour (Material 3's default text theme already
  resolves this to the `onSurfaceVariant`-equivalent tone) — no override, matching what's shipped.
- **What it says with no weekly budget:** does not occur in this phase (every preset default is
  `timeTarget` + a budget), but for completeness and so a future preset default doesn't silently
  regress this: an `outcome`-type goal shows no secondary line at all (inherited, unchanged —
  `_secondaryLine` returns `null` for `GoalType.outcome`) and its `GoalCard` progress track renders
  the Phase 33-locked **empty grey track**, never red (UI-SPEC item 16). If a future change makes any
  preset default to a type with no budget, GOALADD-03 requires that type's row show *something*
  legible in this slot before that preset ships — do not let a silent-attribute regression hide behind
  reused code that happens to return `null` today.
- **Test note, carried from CONTEXT.md:** the regression test for this must find the text
  `"3.0 hrs/week"` (or whatever `weeklyHourBudget` is at test time) rendered on the row — **not**
  assert `goal.weeklyHourBudget == 3.0`, which is a symbolic assertion derived from the same constant
  it's meant to catch drifting, and cannot fail (CLAUDE.md, "Assertions that cannot fail").
- **Emoji lands on the goal, not just the chip:** the shared chip widget's create callback must pass
  the preset's emoji through to the created `Goal.emojiTag` — `GoalsNotifier.quickAddGoals` today
  takes only `Iterable<String> names` and never sets `emojiTag`; it (or a sibling method) must gain an
  emoji parameter. `GoalCard`'s title row already renders `goal.emojiTag` when non-null
  (`goal_card.dart:308-314`) — no card change needed once the data is there. **Verify this on the
  created `Goal` object, not just on the tapped chip** — a chip can carry an emoji purely as its own
  decoration without it ever reaching the model, which is exactly the failure mode CONTEXT.md flags.

### Decision 2 — "add your own" is a button, not a field (the subtlest part of the phase)

The control that was deleted 2026-09-08 was a `TextField`: type, press Enter, a goal is created
outright with an unchosen 3.0 hrs/week budget. **A dashed-border field with placeholder text that
creates on submit is that same control wearing a new location**, regardless of where it sits in the
flow — the prohibition is about the *shape* of the affordance, not merely its screen position.

**Resolution:** "Add your own" is a full-width tappable **row/button** (icon + label, `InkWell` or
`ListTile`-shaped, no border implying a text field, no placeholder text implying "type here") that
**opens `GoalFormSheet`** — the same multi-field form every goal already goes through when its
attributes aren't a hard-coded default. It does not accept typed text itself and does not create
anything on its own.

This is a deliberate asymmetry from presets, and it is the correct one: a preset's attributes are a
generic default the owner has already agreed to accept blind (visible immediately, one tap to fix).
A hand-typed name has no default anyone pre-agreed to — nothing about it can be safely assumed, so it
earns the full form rather than another instant-create path. **Sketch 006 variant B's "chip → form"
behaviour is not dead — it survives here, scoped to exactly the one case ruling (a) doesn't cover.**

- Visual contract: matches `_DoorTile`'s tappable-row shape (leading `Icon(Icons.add,
  color: colorScheme.primary)`, label at `bodyMedium`/`titleSmall`), **not** `_QuickPickSection`'s
  chip family and **not** a `TextFormField`/`OutlineInputBorder` of any kind.
- This satisfies GOALADD-02 ("typing your own is as easy as tapping one") in taps-to-reach terms — it
  is one tap away, exactly like a preset — while satisfying the prohibition in substance, not just in
  wording.

### Decision 3 — the two source widgets disagree; here is the resolution (hard constraint #4)

`_ChipCloud` (onboarding) and `_QuickPickSection` (restoratives) disagree on two axes. Both are
named and resolved rather than silently picked:

**Axis A — chip family and layout.** `_ChipCloud` splits "added" (`InputChip`, removable, own visual
family) from "suggested" (`ActionChip`, `Icons.add` avatar) into two visually distinct groups in one
`Wrap`. `_QuickPickSection` uses one `FilterChip` per preset, toggling `selected` in place, single
group, emoji avatar.

*Resolved:* **the shared widget follows `_QuickPickSection`'s single-`FilterChip`-family shape** —
one `Wrap` of `FilterChip`s, always an emoji avatar (never a generic `+` icon), never a second visual
family for "already added." This matches sketch 006 variant A's own visual treatment (a preset
morphs in place, not into a separately-styled chip elsewhere) and is simpler: one chip type, one
codepath. **Visible change:** onboarding's `_ChipCloud` usages (`_GoalsBeat` and `_RestorativesBeat`)
visibly change from the two-tier Input/Action split to the single-row `FilterChip` grid, and the
goals beat gains emoji avatars for the first time (`_goalPresets` currently has none).
`_QuickPickSection`'s own geometry is preserved — restoratives is the surface whose shipped, already
thumb-tested layout this resolution deliberately does **not** disturb.

**Axis B — what a tap on an already-present preset does.** `_QuickPickSection`: `selected: true`,
tapping again calls `deleteItem` — no confirmation, cheap and reversible (a `RestorativeItem` has no
attributes to lose). `_ChipCloud`: an already-added preset simply never appears as a suggestion again
(`_suggestionsFor` filters it out); there is no "tap a selected chip to remove" gesture at all in
onboarding.

*Resolved:* **the shared widget takes a `mode` distinction, and Goals uses the safer of the two
behaviours.** A `Goal` carries type, budget and priority and has real scheduling consequences — Ruling
6 in `STATE.md` (`Discard` → `Cancel`) shows the owner is already sensitive to a goal disappearing
from a control whose label didn't say so plainly. Re-tapping a chip is exactly that shape of risk: a
second tap on the same visual location, with no confirmation, silently archiving a goal the user may
only have meant to look at again. So:

- **Goals & onboarding (`createOnly` behaviour):** once a preset matches an existing active goal
  (case-insensitive name match, the same idiom as `_suggestionsFor`/`_matchFor`), **the chip is
  hidden from the grid entirely.** It is never shown selected, never shown disabled-but-visible, and
  tapping cannot remove the goal. Removal only ever happens through the existing, deliberate
  `Archive goal` control inside the form.
- **Restoratives (`toggle` behaviour, unchanged):** keeps its exact shipped semantics —
  `FilterChip(selected: true)`, tap-to-remove, no confirmation. A `RestorativeItem` has no attributes
  to lose, and this behaviour already passed (partially — see Deferred Ideas) prior UAT rounds. **This
  phase does not touch restoratives' interaction model, only its implementation source** (backed by
  the shared widget instead of a private one, so geometry and behaviour are provably identical, not
  merely "should be close").
- **Visible change, stated plainly for UAT:** restoratives' chip *behaviour* does not change. Its
  underlying widget does. If geometry drifts by even a pixel, that is a regression to flag — the
  fragile, previously-relitigated tap-target history on this screen (Item 5, unmeasured across Phases
  32-33) means any drift here reopens a question this project has asked five times already.

### Decision 4 — tap feedback, and closing the double-tap race (specific question 3)

Two things must both be true, and CONTEXT.md's mitigation only holds if both are:

1. **Visible confirmation.** The tapped chip vanishes from the grid, and a full `GoalCard` — emoji,
   name, and the `bodySmall` "X hrs/week" line from Decision 1 — appears in a "Just added" section
   directly below the chip grid (above "Add your own" is wrong per the sketch's own ordering; keep
   "Just added" **after** "Add your own", matching the sketch's `chipgrid → qadd → outA` order). No
   `SnackBar`/toast is used — a whole appearing card is a stronger, less missable signal than a
   transient toast on a sheet the user is already looking at, and it avoids stacking a second
   ephemeral UI element on top of a sheet that itself may be transient.
2. **No double-create window.** The chip's removal from the grid must happen **synchronously, in the
   same frame as the tap** — via local optimistic state (e.g., a `Set<String>` of "just claimed"
   names checked before the notifier's async save resolves) — not by waiting for
   `GoalsNotifier.loadGoals()` to complete and rebuild. If the chip stays tappable until the async
   round-trip finishes, a fast double-tap creates two goals from one intended tap — precisely the
   failure this objective calls out by name. **This is a functional requirement, not decoration, and
   it is testable:** tap once, pump exactly one frame (not `pumpAndSettle`), and assert the tapped
   chip is already gone before the future completes.

### Decision 5 — re-visit and the empty-grid case (specific question 4)

A preset is considered "claimed" if any **active** goal's name matches it case-insensitively
(trimmed) — the identical rule `_suggestionsFor`/`_matchFor` already apply, extended to read
`GoalsNotifier.goals` instead of the onboarding/restoratives lists. This applies identically:

- On first open of the sheet in a session.
- On re-opening it later, after some presets already became goals in a prior visit.
- Regardless of whether the matching goal was created via a preset tap, via "Add your own," or
  pre-existed before this phase shipped (e.g. a user who already has a goal named "Reading").

**Onboarding and the Goals screen behave the same way** on this question — one matching rule, read
from whichever notifier the surface already has in scope (`GoalsNotifier` for both the Goals-screen
sheet and onboarding's goals beat; `RestorativesNotifier` for onboarding's restoratives beat, which
also keeps the `toggle` behaviour per Decision 3, so it doesn't hide claimed items — it never did).

**If zero presets remain unclaimed** (all 8 already exist as active goals), the entire "Common"
section — heading and grid together — is omitted. The sheet still offers "Add your own." No
substitute copy ("You've added them all!") is shown; per the text-policy carried from
`33-UI-SPEC.md` items 28-30, an absent section says this without a sentence needing to say it.

### What this phase must NOT introduce, restated for the executor

- No confirmation dialog, spinner, or intermediate step between a preset tap and the goal existing.
  If a plan adds one, it has built (b) and mislabelled it — CONTEXT.md's own words.
- No `TextField`/`TextFormField` anywhere inside `GoalPresetPickerSheet`. "Add your own" is a button.
- No second persistent "Add goal" control on the Goals screen itself — this phase only changes what
  happens *after* the existing single button is pressed.
- No LLM, ranking, frequency-weighting, or personalisation of the preset list — `kCommonGoals` is a
  literal, hard-coded 8-item list, mirroring `kCommonRestoratives`'s own class-doc commitment to the
  same (CLAUDE.md).
- Do not widen `colorScheme.error` (destructive) usage to any part of this flow — no preset tap, no
  chip, no row in "Just added" is ever a destructive action.

### Known test impact (flagged, not owned by this document)

`test/screens/goals_add_fork_test.dart` currently asserts that choosing "Something to make time for"
shows `GoalFormSheet` immediately. Under this contract it now shows `GoalPresetPickerSheet` first;
`GoalFormSheet` is reachable only via "Add your own" or by tapping a "Just added" row. The test's
actual protected invariants — the restorative door never produces a `Goal` or shows `GoalFormSheet`,
and there is exactly one entry point into this whole flow — are unaffected and, if anything,
strengthened (two convergent paths to the same form, not two entry points). The planner should expect
to update this test's goal-door assertions, not its restorative-door ones.
