<objective>
Close **WINDOWS entry 7 / gap `windows-7`**: the user's ticked calendar selection is persisted and
rendered but never reaches the device calendar source, so `device_calendar_plus` imports **every**
calendar on the phone. CAL-02 is violated on the device path.

Proven on the owner's iPhone 2026-10-06 by reading the device's own Hive:
`AppSettings.selectedCalendarIds` held exactly **one** id (`CF8A6881-…`) while the imported
`CommitmentBlock`s carried **at least four** distinct calendar ids, including a holidays calendar and
a birthdays calendar.

**The fix shape is already on disk — copy the Google half.** `GoogleCalendarSource` takes its calendar
ids at **construction** time and substitutes them whenever `listEvents` is called with an empty
`calendarIds` argument (`google_calendar_source.dart:278`), because `CalendarSyncService.sync()`
always passes `const []` as its "every calendar this source is configured for" convention.
`DeviceCalendarSource` never got that treatment: it forwards the empty list straight to the plugin,
and the plugin resolves empty to "all calendars". This plan gives the device source the identical
constructor-time list and threads the device half of the persisted selection into it.

**`CalendarSyncService` is deliberately NOT touched by this plan.** Keeping the fix at the source
boundary (where the Google half already lives) means `sync()` keeps its one convention, and it keeps
this plan's files disjoint from plan 36-09's — these two run in different waves against the same
phase and must not collide on `lib/services/calendar_sync_service.dart`.

Purpose: a schedule that is built from the calendars the user chose, and only those.
Output: a device source that can be told which calendars to read, wired from persisted settings at
both production call sites, with the id list that reaches the plugin asserted in a host test.
</objective>
