<objective>
Plans 36-12 (prune) and 36-13 (persisted skipped list) built the two mechanisms; neither is live yet, because
neither caller passes configured ids or records skipped events. This plan connects them — through **one**
function, `runCalendarSync`, used by both callers.

**Why one function, not two edits.** There are two sync callers today: `checkin_screen.dart`'s `_generate`
and `calendar_settings_screen.dart`'s `_syncAndReport`. Each currently repeats "sync, then on success write
the last-sync time". Adding "and pass the configured calendar set, and record the skipped list" in two places
is precisely the duplicated-definition shape WR-02 was raised about in this phase — two callers computing the
set two ways is how a prune deletes the wrong thing. It also makes check-in's behaviour testable without a
new widget seam: `CheckinScreen` builds its source internally from settings and has no injection point, so
the honest place to prove what check-in records is a function it calls.

**The configured set is `selectedCalendarIds ∪ icsUrls`.** Every source stamps each event's `calendarId`
with exactly one of those strings (device: the raw EventKit id; Google: the `google:`-prefixed id; ICS: the
feed URL — see 36-12's objective). On iOS `icsUrls` is unused by the factory, and on desktop/web
`selectedCalendarIds` is unused — the union is therefore conservative: it can only keep more, never delete
something a source was built from.

**Entry 10 closes in code here:** `_skippedBanner` stops reading the screen's in-memory `_lastSyncResult`
and reads `SettingsNotifier.lastCalendarSyncSkipped`. The in-memory field is removed if nothing else reads it.
The banner's copy and position are unchanged (locked; 36-09).

**Entry 11 becomes user-visible here**, including on the desktop/web path, where the LOCKED "Remove this
calendar?" body says "Commitments already imported from it will disappear the next time you sync" — that
sentence becomes true by this plan, and a test proves it through the real removal dialog.

**`_disconnectGoogle`'s doc comment must be corrected, not just deleted.** It says the ICS sentence "is not
true today; `sync()` only ever upserts" — that stops being true. But Disconnect leaves the `google:` ids in
the selection, so the Google child fails (no token) and neither prune touches those blocks — which is what
its own dialog promises ("stay on your schedule until you remove them"). Say exactly that, and say that
there is no in-app removal path for those rows until the user reconnects and unticks (36-17 logs it).

Purpose: one sync definition; a disclosure that persists; a prune that actually runs.
Output: `lib/providers/calendar_sync_runner.dart`, both callers moved onto it, and the banner reading
persisted state.
</objective>
