<objective>
CALAUTH-03, which is the requirement with teeth and the one most likely to pass vacuously. The owner
knowingly accepted a 7-day refresh-token expiry (ROADMAP, CONTEXT). The price of that acceptance is
that when the token dies, the app must **say so** — and must not say so when it is merely offline.

Purpose: telling someone "you're offline" when their login actually expired, or telling them "your
login expired" when the wifi dropped, are both the silently-wrong state CALAUTH-03 exists to
prevent. The discrimination between the two IS the requirement. A test that only ever exercises the
happy path proves nothing about it.

Output: a three-way failure classification inside `GoogleAuthClient`, a real cancellation path, and
the reconnect flag's full lifecycle — each proven against the specific wire shape it keys off.

## What is verifiable here, and what is not

| Claim | Who can settle it | With what |
|---|---|---|
| Given a `400` body containing the expired-or-revoked error, the flag is set and nothing else sets it | the executor, on danserver | `flutter test`, via the injected refresher seam |
| Given a timeout or a 5xx, the flag is NOT set | the executor, on danserver | `flutter test` |
| A cancellation writes nothing | the executor, on danserver | `flutter test` |
| That Google's real endpoint actually emits that body shape after 7 days | **the owner, after a week** (plan 36-07, item 5) | his own phone, a week later |

Everything here runs on danserver because every external call goes through a seam plan 36-01 built.
The fixtures are built from Google's documented and independently corroborated error shape, not from
a live capture — nobody on this machine can produce one.

Decisions implemented: **D-36-01** (Canopy holds and inspects its own token, which is the whole
reason this classification is possible at all).

    - An access token that has not expired is used as-is: the refresher seam is never called at all.

A persisted flag that is only ever set is worse than no flag: the app would keep telling the owner his
login expired forever after the first expiry. Close the lifecycle.

Two paths clear it, and only two: a successful interactive `connect()`, and a successful silent
refresh. Both already exist from Tasks 1 and 2 — this task's job is to prove the clearing happens and
that no OTHER path clears it (in particular, a failed refresh must not clear it, or the reconnect card
would flicker away on every offline sync).

Tests to add:
- Flag set, then a successful `connect()`: flag is false afterwards, new tokens persisted.
- Flag set, then a successful refresh: flag is false afterwards.
- Flag set, then a refresh that fails on the network: flag is still TRUE afterwards.
- Flag set, then a cancelled `connect()`: flag is still TRUE afterwards. Backing out of the reconnect
  sheet does not pretend the problem is solved.
- Flag set, then `disconnect()`: flag is false and tokens are gone — disconnected is not "expired",
  and the screen must fall back to the plain not-connected CTA rather than nagging about a login the
  user deliberately ended.

Then add a doc comment on the flag's declaration in `AppSettings` naming exactly these five outcomes,
because the next person to touch this will reach for a sixth.
