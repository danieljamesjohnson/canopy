<objective>
Close **WINDOWS entries 12 and 13**, both found on the owner's iPhone on 2026-11-02, and remove the
list-teardown half of entry 14's suspected mechanism.

**Entry 12.** The device section shows "Allow calendar access" on every re-open even though permission is
granted and syncs work, because `_mobileFuture` is null in every new `State` and is only ever set by a tap.
It is the device twin of entry 6, which plan 36-10 fixed for Google only. The owner took the CTA for a sync
button. **Fix:** on first build, read the current permission through a call that *cannot* prompt; if
granted, list calendars and show them; never request. `device_calendar_plus` 0.8.0 provides exactly this:
`DeviceCalendar.instance.hasPermissions()` — "Returns the current [CalendarPermissionStatus] without
prompting … never shows the system dialog" (`device_calendar_plus-0.8.0/lib/device_calendar_plus.dart`
lines 104-112), and on iOS `PermissionService.hasPermissions()` returns `getCurrentPermissionStatus()` with
the comment "A status check triggers no prompt" (`device_calendar_plus_ios-0.7.0/.../PermissionService.swift`
line 143). `autoPermissions` is unused in `lib/`, so `listCalendars()` cannot prompt either.

**Why a separate capability interface, not a fifth `CalendarSource` verb.** ROADMAP Phase 36 decision 3:
"If this phase finds itself changing the interface, that is a signal something is wrong."
`google_calendar_source_test.dart` also pins `GoogleCalendarSource` to exactly four `Future` verbs. Only
the device source has a prompt-free status read, so it alone implements a new one-method
`CalendarPermissionReader`; the screen restores only when its device source is one. This also keeps every
existing screen test valid: their `_FakeCalendarSource` is not a reader, so they still start at the CTA,
which is still correct behaviour for a source that cannot read status.

**Restore lists only; it does not sync.** Mirrors 36-10's `_loadGoogleCalendars`. Opening a settings
screen should not rewrite the schedule — and after plan 36-12, a sync can delete blocks. The skipped-events
banner comes from persisted state (plans 36-13/36-15), and "Sync now" is one tap away. D-35-10 ("no
permission result is ever persisted") is honoured: status is read live on every open and stored nowhere.

**Entry 13.** "Sync now" on mobile currently re-runs the whole permission flow — it re-requests permission,
re-lists calendars and replaces the device section with a spinner — and its only result is a `bodySmall`
status line changing from "Synced 5m ago" to "Synced just now". The owner "had no idea" anything happened.
**Fix:** sync in place. The button disables and shows a 16dp spinner while running; on success a SnackBar
carries the **locked** status string (`35-UI-SPEC.md` Copywriting Contract, "Sync status (fresh)":
"Synced {relative time} — {n} commitments imported"); on failure the existing locked failure SnackBar.

**No new user-visible string.** The success SnackBar is a NEW PLACEMENT of locked copy — placement
proposed-not-locked, wording locked and reused through one helper so the footer and SnackBar cannot drift.
The in-flight state is a spinner beside the unchanged "Sync now" label, following the UI-SPEC's own
"Requesting (in flight)" idiom of a spinner with no copy.

**Also fixed, because it is the same defect class as 13:** the footer computes its time from the last
attempt's `syncedAt` before falling back to the persisted success time, so a FAILED sync renders as
"Synced just now". The footer reads only the persisted success-only time.

**Deliberately unchanged:** the desktop/web branch's "Sync now". It already replaces the body with a
spinner while it reloads, no defect was reported there, and changing it is outside these entries. Record
this in the SUMMARY so the asymmetry reads as a decision.

Purpose: a Calendars screen that remembers you said yes, and a sync button that answers back.
Output: `CalendarPermissionReader`, `DeviceCalendarSource.currentPermission()`, a restore path, and an
in-place "Sync now".
