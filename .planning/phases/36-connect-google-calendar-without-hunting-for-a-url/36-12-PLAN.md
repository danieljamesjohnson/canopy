<objective>
Close **WINDOWS entry 11**: `CalendarSyncService.sync()` only ever upserts, so an unticked calendar's
blocks and a deleted event's block stay on the schedule forever. Observed on real data on 2026-11-02:
a "Bi-Weekly One on One" (calendar hash `9fb91958`) imported while Home was ticked survived the owner
switching to spunkl. `35-UI-SPEC.md`'s **locked** "Remove this calendar?" body promises the opposite.

The established design constraint is honoured, not argued with: a window-scoped prune is unsafe while
`CompositeCalendarSource` swallows a per-child failure and returns a partial list with no signal. So
this plan builds the prune in the two halves that constraint allows.

1. **Selection prune — needs no fetch, runs on every sync including a failed one.** Every imported
   block's `externalEventId` is `ics:<calendarIdHash(calendarId)>:<uid>:<recurrenceId><daySuffix>`
   (`_buildBlock`). Every source stamps `calendarId` with the exact string the user's configuration
   stores: device events carry the raw EventKit id (R1 proved `hash(E3B52CDB-…) = 9c7d030a` on the
   owner's phone), Google events carry the `google:`-prefixed id (`google_calendar_source.dart:311`),
   ICS events carry the feed URL (`ics_calendar_source.dart:99`). So "is this block's calendar still
   configured" is a set-membership test on the hash, with no network call at all.
2. **Event prune — only for sources that verifiably succeeded, only on fully covered days.** A new
   per-child success signal on `CompositeCalendarSource` says which children actually answered. A
   block is pruned for a missing event only when its calendar belongs to a child that succeeded, and
   only when its date is a day the fetch window covered end to end.

**Decided here, recorded so it is not re-litigated:**
- The selection prune runs even when the fetch fails ("do that unconditionally", per the gap brief).
  The user's own configuration says the calendar is gone; that is true whether or not the network is.
  `CalendarSyncResult.failed`'s doc comment and the T-35-01 comment in `sync()` must be corrected to
  say so — they currently promise "no block was touched".
- `configuredCalendarIds` is **opt-in** (null = no selection prune). This plan does not touch either
  caller; plan 36-15 wires both through one shared function so the two callers cannot compute the set
  differently (the WR-02 failure shape). The event prune needs no new input and is live as soon as this
  merges.
- Today is excluded from the event prune. A fetch starting at "now" may not return an event that
  already ended this morning (EventKit's partial-overlap semantics are not verified on hardware), and
  deleting it would rewrite today's plan on the next ⟳ Re-check-in. **Accepted cost:** an event deleted
  today keeps its block for the rest of today. Say so in the SUMMARY and in the class doc.
- An unknown source type (anything not `DeviceCalendarSource`, `GoogleCalendarSource` or
  `IcsCalendarSource`) is **default-deny** for the event prune: it never authorises a delete.
- **Not changed, and recorded for 36-17 to log:** after Google Disconnect, `google:` ids stay in
  `selectedCalendarIds` (the Disconnect dialog promises imported commitments stay), and the Google
  child fails without a token — so those blocks are neither selection- nor event-pruned and have no
  in-app removal path until the user reconnects and unticks. That is the Disconnect dialog's own
  promise and is not this plan's to reverse.

`lib/services/schedule_generator.dart` must stay byte-identical — gated below.

Purpose: an imported schedule that follows the calendar, in both directions.
Output: a pruning `sync()`, a per-child success signal, and ID-level tests that prove what survives.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| calendar source answer -> local Hive | a partial or failed answer must never be read as "these events were deleted" |
| user configuration -> prune decision | only the user's own persisted selection decides which calendars are gone |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-36-44 | Tampering | `sync()` prunes | critical | mitigate | A hand-entered commitment has no source to be re-derived from, so deleting one is unrecoverable data loss. Both prunes require `isFromCalendar == true`; a dedicated fixture per prune (a hand-entered block carrying a matching hash — for the event prune, on a verified calendar, dated tomorrow, absent from the fetch) makes each guard load-bearing on its own, and a mutation removing either guard must fail at runtime (Task 1 mutation a, Task 3 mutation e). |
| T-36-45 | Denial of Service | event prune vs `CompositeCalendarSource` | high | mitigate | A network blip on one child would otherwise delete a healthy calendar's blocks. The event prune trusts only children `listEventsByChild` reports as succeeded, an unknown source type is default-deny, and a failed fetch runs no event prune (Tasks 2-3, each mutation-proven). |
| T-36-46 | Tampering | window edges | medium | mitigate | An event that ended earlier today, or one on the window's partially fetched last day, may be absent from a correct answer. Only days strictly inside the fetch window are event-pruned, proven by two survival tests and two mutations (Task 3). |
| T-36-47 | Repudiation | `CalendarSyncResult.failed` doc | low | mitigate | The doc comment and the T-35-01 comment currently promise a failed sync touches nothing; both are rewritten to state the selection prune still runs (Task 1). |
| T-36-SC | Tampering | npm/pip/pub installs | high | accept | No package-manager install task exists; `pubspec.yaml` is not modified. D-36-04's audit stands. |
