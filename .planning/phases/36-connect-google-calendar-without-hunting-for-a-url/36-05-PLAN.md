<objective>
D-36-03, in code: both iOS calendar sources coexist and the user ticks per calendar. Plus the
mitigation that ruling was made conditional on — detecting when the same underlying calendar has been
ticked under both sources, so the picker can say so.

Purpose: the owner chose "both" against the recommendation, **with the footgun on screen**: ticking
`dan@gmail.com` under GOOGLE and under THIS DEVICE yields every meeting twice. He chose it because
it is the only option that keeps device-only calendars — iCloud Personal, a local calendar, a
subscribed feed added at OS level — reachable while signed in to Google. Replace-on-sign-in would
have dropped those silently, which is quieter and worse.

That ruling is defensible **only with its mitigation**, and D-36-03 says the mitigation is REQUIRED,
not advisory. This plan builds the detection; plan 36-06 puts it on screen. The precedent is Phase
34's D-(a): *"the danger is not that a default exists, it is that the default is invisible."* Here
the danger is not that both sources exist, it is that double-ticking is invisible until the day comes
back doubled.

Output: a composite source, an extended factory, and a pure overlap detector.

## What is verifiable here, and what is not

| Claim | Who can settle it | With what |
|---|---|---|
| Two sources fan out and fan in correctly; one child's failure does not zero the other | the executor, on danserver | `flutter test` |
| The detector's RULE — given these calendars and these ticks, flag exactly these pairs | the executor, on danserver | `flutter test` over hand-built inputs |
| The detector's INPUTS — what a real iPhone's EventKit actually reports as `accountName` for a Google calendar, and whether it lines up with what Google's API reports | **the owner, on his MacBook** (plan 36-07, item 6) | a real device, a real double-tick |
| Whether the warning reads clearly enough to stop him doing it by accident | **the owner** (plan 36-07, item 6) | his own eyes — no widget test settles this |

**The detector's precision cannot be proven here.** Its rule can. That distinction has to survive into
the SUMMARY rather than being flattened into "overlap detection works".

Decisions implemented: **D-36-03** (both sources coexist, per-calendar ticking, and the REQUIRED
overlap mitigation), **D-36-01** (iOS only; the browser build keeps the `.ics` path untouched).

D-35-12 established "one active source type per platform, never a combined multi-source picker", and
`calendar_source_factory.dart`'s own doc comment says so today. **D-36-03 overrides it for iOS
specifically**, and research flagged that it must be stated as a narrow, deliberate carve-out rather
than quietly violated. Update that doc comment to say so, naming both decisions.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| two independent calendar sources -> one sync | A failure or a slow response in either crosses into the other's result |
| the user's selection -> what actually gets imported | The picker is the authority; a source that imported an unticked calendar would violate CAL-02 |
| the overlap detector -> the user's trust | A warning that fires wrongly is worse than no warning (D-36-03's own words) |
