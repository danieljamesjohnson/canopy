### The one open question, now answered from the code — read this before planning anything around it

**`CalendarSyncService.sync()` does NOT prune. It only ever upserts.** Evidence, three independent
reads:

1. `sync()` (lines 149-176) calls `_repository.getAll()` and then only `_repository.save(block)` for
   blocks it produced this run. There is no `delete` call anywhere in the method or in `_mapEvent`.
2. `grep -rn '\.delete(' lib/` returns four call sites, none of them in the calendar path:
   `restoratives_notifier`, `schedule_notifier` (×2, schedule re-anchoring) and
   `commitments_notifier.removeBlock` (a user-initiated removal).
3. The codebase already says so out loud. `calendar_settings_screen.dart`'s `_disconnectGoogle` doc
   comment explains why its dialog copy deliberately differs from the ICS removal dialog's:
   *"that sentence is not true today; `sync()` only ever upserts."*

**So the six fake blocks on the owner's phone would survive any number of re-syncs.** An explicit
one-time cleanup is required, which is exactly the remedy D-36-05 sanctions ("the owner needs either a
migration or an explicit instruction"). Task 2 is that migration.

**Why the cleanup deletes every imported block and not just the all-day-shaped ones.** The pre-fix
imported set is untrustworthy on *both* axes this gap closure changes: *which calendars* were read
(plan 36-08 — the owner's selection was being ignored, so blocks exist from a holidays and a birthdays
calendar he never ticked, and those calendars will no longer be queried at all, so an all-day-shaped
sweep could never reach them) and *which events* were imported (this plan). The data is derived and
fully re-derivable from the source. Discarding it and re-deriving is the only option that guarantees
the next device judgement is made against post-fix data — which this project's own CLAUDE.md trap #4
makes a hard requirement, naming the date a UAT judged pre-fix data and cost the owner a round trip.
A shape-matching sweep (`startMinutes == 480 && endMinutes == 1320`) was considered and rejected: it
cannot reach blocks from calendars that are no longer queried, and it would delete a genuine timed
08:00-22:00 event on a false positive.

**The accepted cost, stated plainly:** for one check-in immediately after the upgrade, if the calendar
source cannot be read at all (offline), there are no last-known imported blocks to degrade to — D-35-13's
guarantee is weakened for exactly that one window. The remedy is one successful sync, which plan 36-11's
re-verification document makes its mandatory first step.

Purpose: a schedule that no longer blanks a day because someone's birthday is in it, with the
omission visible at the top of the screen rather than buried at the bottom.
Output: `SkipReason.allDay`, its locked label, the skipping branch, a one-time data migration, and the
disclosure promoted to a top-of-screen banner.
