<objective>
The tracer: prove the whole Google path end-to-end, in one thin slice, before anything is built out
horizontally. A faked consent launcher returns a token, the token is persisted to Hive, a faked HTTP
client returns Google's own `events.list` JSON, and the EXISTING `CalendarSyncService` turns it into a
`CommitmentBlock`. Every layer this phase will touch is wired; none of them is built out yet.

Purpose: this phase's riskiest architectural claim is that a Google token can be held by the app
itself (D-36-01) and that its events reuse Phase 35's proven mapping layer wholesale (CONTEXT
decision 3). Proving that on the executor's best early-context tokens catches an architectural
dead-end after one commit instead of after six.

Output: `google_oauth_config.dart`, `google_auth_client.dart`, `google_calendar_source.dart`, four
additive `AppSettings` fields with migration 11 to 12, and one end-to-end test.

**`lib/data/calendar/google_auth_client.dart` — the token lifecycle behind two seams.**
Declare, in this file:

- `class GoogleTokens` — a plain value class carrying `accessToken`, nullable `refreshToken`, and
  `expiresAt`.
- `abstract class GoogleTokenStore` — `read()`, `write(GoogleTokens)`, `clear()`, plus
  `setReconnectNeeded(bool)` and a `reconnectNeeded` read. This is the seam that keeps every test in
  this phase off Hive.
- `typedef GoogleAuthLauncher = Future<GoogleTokens?> Function({required String clientId, required String redirectUri, required List<String> scopes})` — **returning null means the user cancelled.**
  A cancellation is a real state, not an error (RESEARCH Anti-Patterns); representing it as a null
  return rather than an exception is what lets a test drive it with no native sheet.
- `typedef GoogleCredentialsRefresher` — a seam over `googleapis_auth`'s `refreshCredentials`, taking
  a `ClientId`, an `AccessCredentials` and an `http.Client`.
- `class GoogleAuthException implements Exception` — same one-field shape as `IcsSourceException`.
  Deliberately carries no token material in its message.
- `class GoogleAuthClient` — constructor takes the store plus optional overrides for both seams and
  for the client ID, each defaulting to the production implementation.

The production launcher lives in this file and is the **only** place in `lib/` that imports
`package:flutter_appauth`. It calls `authorizeAndExchangeCode` with the reversed-client-ID redirect
URI, Google's authorization and token endpoints, the single read-only scope, and the additional
parameters that make Google issue a durable refresh token for an installed app. Research flagged the
exact parameter-passing mechanism as Assumption A8 — confirm it against the installed package's own
source and say in the SUMMARY which shape you found, rather than copying the research snippet blind.
It catches `FlutterAppAuthUserCancelledException` **specifically** and returns null for it; anything
else becomes a `GoogleAuthException`.

This task implements only the success and cancellation paths plus a single generic failure branch.
The three-way failure classification CALAUTH-03 actually requires is plan 36-02's whole subject — do
not pre-empt it here with a half-version, and do not collapse the seams to save a file, because that
classification is why research split this file out in the first place.

Give the client: `connect()` (run the launcher, persist on success, clear the reconnect flag,
return whether the user cancelled), `hasCredentials()`, `authenticatedClient()` (read the stored
tokens, refresh if expired, hand back an `http.Client` that carries the bearer token), and
`disconnect()` (clear stored tokens and the flag).

**`lib/data/calendar/google_calendar_source.dart` — the fourth `CalendarSource`.**
`GoogleCalendarSource implements CalendarSource`, constructed with a `GoogleAuthClient`, the list of
selected Google calendar ids, and an optional `GoogleApiClientFactory` seam so tests supply their own
`http.Client`. All four verbs implemented for real:

- `isAvailable()` — a one-line predicate over stored-credential presence, mirroring
  `IcsCalendarSource`'s "no URLs configured reads as false". Not-yet-connected is `false`, never a
  throw.
- `requestPermission()` — runs the interactive connect and maps the outcome onto
  `CalendarPermissionState`: consent completed maps to `granted`; **a user cancellation maps to
  `notDetermined`, NOT `denied`.** `denied` drives the settings screen's denied card, which is the
  wrong surface for someone who simply backed out of a sheet; `notDetermined` returns them to the CTA
  with nothing on screen implying a fault. Say this in the method's doc comment so it is not
  "corrected" later.
- `listCalendars()` — `CalendarApi(client).calendarList.list()`, mapped to `CalendarInfo`. Prefix
  every id with `google:` so a Google calendar id can never be confused with a device calendar id in
  the persisted selection (plan 36-05 depends on this being unambiguous), and strip that prefix
  before it is ever sent to Google. Full mapping and fixtures are plan 36-03's job; here it needs to
  be real and correct, not exhaustively tested.
- `listEvents(...)` — for each configured calendar id, call `events.list` with `singleEvents` true
  and `showDeleted` true, the window as `timeMin`/`timeMax`, and follow `nextPageToken` until
  exhausted. `singleEvents` is what expands recurrences with their exceptions applied — the defect
  the ICS path provably cannot fix — and `showDeleted` is what makes a cancelled occurrence come back
  as a stub instead of silently vanishing. Both are deliberate and neither is the API default;
  comment them as such.
  Follow `IcsCalendarSource.listEvents`'s own convention for the `calendarIds` argument: an EMPTY
  list means "every calendar this source is configured for", because that is exactly what
  `CalendarSyncService.sync()` passes.

Add `GoogleSourceException` following `IcsSourceException`'s shape, and let every network/API failure
surface as it, so `CalendarSyncService`'s existing catch-all degrades a Google failure exactly the
way it already degrades an ICS failure.

**Never call a mutating verb on `CalendarApi`.** The `CalendarSource` interface declares no write
verb so nothing downstream can ask for one; this file is the only place a write call could physically
be reached from, and the read-only scope means Google would refuse it anyway. That belt-and-braces
pairing is the point of CONTEXT decision 2 — it is enforced by Google, not by our discipline.
