<objective>
Close **WINDOWS entry 6**, the last open entry a reasonable person reports as a bug: re-opening the
Calendars screen always shows "Connect Google Calendar" even when a valid token is stored, because
`_buildGoogleSection` reads only `reconnectNeeded` (a *dead* token) from persisted state and never a
valid-but-unconfirmed connection. Tapping it re-launches real Google consent and re-issues a token, so
this is UX friction rather than wrong data — which is exactly why it is scheduled **last**.

**Deliberately placed in wave 3, behind both gap plans.** Gaps 7, 8 and 10 are what make the owner's
schedule wrong; this one makes it annoying. It shares
`lib/screens/settings/calendar_settings_screen.dart` with plans 36-08 and 36-09, so it cannot run
beside either of them in a worktree-parallel wave, and if it had to be dropped it would be the one to
drop. It is not being dropped — it is being sequenced.

Code-review finding **WR-05** compounds this entry and is **not** fixed here: a transient
`listCalendars()` failure after a successful permission still folds into `connected: false` and shows
the CTA. The restore path added by this plan inherits that same shape on purpose — introducing a
fourth Google state would need new user-visible copy, and copy belongs to an owner-reviewed UI-SPEC,
not to an agent. Record it in the SUMMARY as still open rather than quietly widening scope.

Purpose: a screen that remembers you are signed in.
Output: a `SettingsNotifier.googleConnected` getter derived from the same persisted fields
`GoogleTokenStore.read()` guards on, and a Google section that restores itself from it by listing
calendars — never by asking Google for consent again.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| persisted token state (Hive) → screen state | the screen's claim about whether the user is connected must come from stored data, not from in-session memory |
| app → Google's consent endpoint | every launch of the consent sheet is a real authorization request against the user's Google account |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-36-38 | Spoofing | `_buildGoogleSection` restore path | medium | mitigate | Showing a consent sheet the user does not need trains them to approve consent screens without reading them, which is the precondition for a real phishing success later. The restore path calls `listCalendars()` only; proven by a `requestPermissionCount == 0` assertion and mutation-proven by making it re-consent (Task 2). |
| T-36-39 | Tampering | `SettingsNotifier.googleConnected` vs `GoogleTokenStore.read()` | medium | mitigate | Two answers to "is there a token" that can drift would let the screen claim connected while the auth client throws `not connected`. The getter is derived from the same two cached fields `read()` guards on, with a doc comment binding them, and `clear()`/`setReconnectNeeded()` are covered by their own state tests (Task 1). |
| T-36-40 | Repudiation | CALAUTH-03's reconnect card ordering | high | mitigate | If the restore branch were evaluated before the `reconnectNeeded` check, a dead token would render as connected and the calendar would be silently stale — the exact failure CALAUTH-03 exists to prevent.
