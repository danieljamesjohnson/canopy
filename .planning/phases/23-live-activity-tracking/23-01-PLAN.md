<objective>
Make a running break a first-class current activity. `resolveNowState` stops filtering to work
chunks, every place that renders a chunk's title becomes break-aware, and the AppBar's "Start
focus" button stops being able to target a break.

Purpose: LIVE-01 — the screen always names what the user is doing right now. Today, during a
break, `resolveNowState` skips the break entirely and returns `GapBeforeNext`, so the screen says
"next chunk at 8:00" while the user is actually resting. That is the reported bug.

Output: a break-aware now-state, two named title helpers, a break-excluded focus target, and the
regression coverage for all three.

**Locked decisions implemented here** (IDs assigned to `23-CONTEXT.md`'s numbered decisions —
CONTEXT.md numbers them 1-4 plus a "Care with the existing state machine" section; this plan set
refers to them as D-01…D-06 throughout):

| ID | Source | Content |
|----|--------|---------|
| D-01 | CONTEXT decision 1 | Countdown granularity: whole minutes rounded up at ≥60s, seconds at <60s; no blanket 1-second timer — **implemented in plan 23-02** |
| D-02 | CONTEXT decision 2 | Breaks are a first-class current activity: `resolveNowState` must include them; copy is "Taking a break" / "Taking a long break" under a "RIGHT NOW — RESTING" kicker; a break shows **no** Complete/Skip |
| D-03 | CONTEXT decision 3 | Edge-state copy for pre-start / gap / day-complete — **implemented in plan 23-03** |
| D-04 | CONTEXT decision 4 | Progress bar on the current activity, filling left-to-right across its window |
| D-05 | CONTEXT "Care with the existing state machine" | The KEY INVARIANT (clock window found FIRST by time, THEN resolution checked) must survive; the five subtypes are the extension point and must not be collapsed or bypassed |
| D-06 | CONTEXT "Care with the existing state machine" | Extend the existing `resolveNowState` unit tests rather than replacing the pattern; keep the injectable clock |

This plan implements **D-02, D-04, D-05, D-06**.

**Planner decisions made here** (stated so the executor does not re-litigate them):

- **P-2 — where break-awareness lives.** RESEARCH Open Question 2 left helper placement to the
  planner. Decision: two private methods on `_TodayScreenState`, colocated with `_chunkTitle`,
  **not** promoted to `time_format.dart` or `now_state.dart`. No other screen renders a chunk
  title (`chunk_card.dart` hardcodes its own break strings), so there is no cross-file reuse
  pressure yet, and keeping them private keeps every `chunkType` conditional inside a named,
  greppable helper (RESEARCH Pitfall 1).
- **P-3 — two title vocabularies, deliberately.** `_chunkTitle` returns the *reference* name
  ('Short break' / 'Long break') used wherever a break is mentioned but is not the live row.
  `_liveTitle` returns the *present-continuous* name ('Taking a break' / 'Taking a long break')
  used only by the live row. Rationale: "Next · Taking a break at 9:25" is tense-mismatched for a
  future event, and 'Short break'/'Long break' already ships and is tested in
  `chunk_card.dart:92-94` on this same screen (RESEARCH Assumption A3).
- **P-4 — focus-target exclusion shape.** Keep the existing exhaustive `switch (nowState)` and
  narrow its result afterwards. Do not add a `chunkType` check inside `IconButton.onPressed` or
  anywhere else — that would be a second, competing gate.

**Planner finding not present in RESEARCH — read this before worrying about `DayComplete`.**
Broadening the filter raises an obvious question: if a break can now be `scheduled.last`, does the
day stop reading as complete until a trailing break's window ends, and can an all-work-resolved
day return `GapBeforeNext(trailingBreak)` instead of `DayComplete()`? **No.**
`schedule_generator.dart` STEP E (`while (result.isNotEmpty && result.last.chunkType !=
ChunkType.work) result.removeLast();`) trims trailing non-work chunks precisely so there is never
a dangling break at the end of a generated day. The last chunk of any generated schedule is always
work-typed, so neither the `DayComplete` window check nor the all-resolved fallback changes
behaviour. Task 1 adds a regression test that locks this in rather than leaving it as reasoning.
</objective>
