# Phase 16 — UI Design Contract

> Visual and interaction contract for Phase 16: Priority Model Reconciliation.
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.
>
> **Scope note:** This is a correctness reconciliation of existing UI surfaces,
> not net-new screens. The contract focuses on three things:
> (1) the priority chip's visual states and the priorityWeight-to-label mapping,
> (2) the goal-sheet modal layout/height contract so Priority + Save are always
>     reachable for every goal type,
> (3) the interaction contract between drag-reorder and the priority selector so
>     the chip never goes stale.

## Priority Weight Bands — Canonical Mapping

This is the single source of truth for converting between `priorityWeight` (double, 0.0–1.0) and the Low/Normal/High label displayed in the UI. The executor must use this exact mapping in all logic.

| Label | Weight written by form selector | Weight range that displays this chip | Band boundary |
|-------|---------------------------------|--------------------------------------|---------------|
| High | `0.75` | `>= 0.75` | inclusive at 0.75 |
| Normal | `0.5` | `> 0.25 && < 0.75` | exclusive on both ends — no chip rendered |
| Low | `0.25` | `<= 0.25` | inclusive at 0.25 |

**The reconciliation problem (PRIORITY-03):** `reorderAllWithPriority` uses a linear spread formula: `high - (high - low) * i / (n - 1)` where `high = 0.75`, `low = 0.25`. For a list of 2 goals this yields exactly `{0.75, 0.25}`. For 3 goals: `{0.75, 0.5, 0.25}`. For 4+ goals, intermediate positions land at non-band-boundary values like `0.583…` or `0.416…` — which correctly render as Normal (no chip). The bug occurs when a goal that previously had `priorityWeight = 0.75` (High) is dragged to position 1 of 4, yielding weight `≈ 0.583` — which drops its chip silently.

**Resolution contract:** After any drag, the chip shown must reflect the NEW weight assigned by `reorderAllWithPriority`, not the previous weight. The state refresh already happens via `notifyListeners()` inside `reorderAllWithPriority → loadGoals()`. If the chip appears stale, the bug is in the Consumer rebuild, not the mapping. The executor must verify the `GoalCard` rebuilds via `Consumer<GoalsNotifier>` after `reorderAllWithPriority` completes.

## Goal Form Priority Selector — Interaction Contract

**Widget:** `SegmentedButton<double>` with three segments: `Low (0.25)`, `Normal (0.5)`, `High (0.75)`.

**Default state for new goals:** `Normal` selected (weight `0.5`). This matches the null coalesce in `SegmentedButton`'s `selected: {_priorityWeight ?? 0.5}`.

**State propagation on save:** `_priorityWeight` state variable is written to `goal.priorityWeight` in `_save()` before calling `notifier.saveGoal(goal)`. After save, `notifier.saveGoal` calls `loadGoals()` which calls `notifyListeners()`. The `Consumer<GoalsNotifier>` in `GoalsScreen` must rebuild `GoalCard` instances, causing `_PriorityChip` to re-evaluate with the new weight. No restart required.

**Interaction rules:**
1. Selector tap → `setState(() => _priorityWeight = val.first)` — updates local form state only.
2. Save tap → persists `_priorityWeight` to the `Goal` object → `notifier.saveGoal()` → list rebuilds.
3. Drag in list → `reorderAllWithPriority` → `loadGoals()` → list rebuilds — selector state is NOT touched (form is closed during drag).
4. The two write paths are independent: drag sets weight via position formula; form selector sets weight via explicit discrete value. Both write to `Goal.priorityWeight`. The chip reads `Goal.priorityWeight`. There is no third source of truth.

**Conflict rule:** If a user drags a goal to position 2 of 5 (weight ≈ 0.625, Normal tier, no chip), then opens the form, the priority selector must show `Normal` selected — because `_priorityWeight` initializes from `goal.priorityWeight` in `initState`. This is correct behavior — drag outcome IS the state.

## Goal Sheet Modal Layout Contract

**Shell:** `DraggableScrollableSheet` inside `showModalBottomSheet` with `isScrollControlled: true`, `useSafeArea: true`.

**Sizing:**

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `initialChildSize` | `0.6` | Shows ~60% of viewport on open — enough for name + type picker + priority selector |
| `minChildSize` | `0.4` | Minimum drag-down resting position |
| `maxChildSize` | `1.0` | Full viewport on drag-up |
| `snap: true` | enabled | Snaps to 0.6 or 1.0 |
| `snapSizes` | `[0.6, 1.0]` | Two snap positions |

**The GOALFORM-02 problem:** The existing test resizes the surface to `Size(800, 1200)` and pumps the form directly (not inside the modal). This means it never exercises the actual modal frame. For a real device at `initialChildSize: 0.6`, the modal occupies 60% of the screen height. On a 844pt iPhone (logical height), that is ~506pt. The form content for an outcome goal (the deepest variant: drag handle + title + type picker + name field + priority selector + date picker row + description textarea + archive button + Cancel/Save row) must fit inside this 506pt with scroll, or the Save button is clipped below the fold if the sheet cannot be dragged to full height.

**Layout requirement:** The form MUST be `SingleChildScrollView`-wrapped (already implemented). The `DraggableScrollableSheet` `scrollController` is passed to `SingleChildScrollView` (already implemented). This means scrolling within the sheet IS possible, and the user can always reach Save by scrolling — even at `initialChildSize: 0.6`. The test contract is: at the TRUE `initialChildSize: 0.6` modal height (not `1200px`), the Priority selector and Save button are findable via `scrollUntilVisible`, not merely `find.text(...)` with an oversized surface.

**Restructure condition:** If outcome goals overflow even at `maxChildSize: 1.0` on a 320pt-wide device, restructure the layout. Current assessment: unlikely — `SingleChildScrollView` handles it. Do not restructure unless the GOALFORM-02 test written at true modal height actually fails at `maxChildSize: 1.0`.

**Test surface contract (GOALFORM-02):** The new test must:
1. Use the ACTUAL opened modal height — computed as `tester.view.physicalSize.height * 0.6 / tester.view.devicePixelRatio` (or equivalent) — NOT `Size(800, 1200)`.
2. Pump `GoalFormSheet` inside a modal (via `showModalBottomSheet` + `DraggableScrollableSheet`) using the existing `pumpWithMood` helper.
3. For each goal type (time-target, outcome, habit): after opening the modal at `initialChildSize: 0.6`, assert Priority (`SegmentedButton<double>`) and Save (`ElevatedButton` labeled "Add goal" or "Save") are reachable via scroll — not merely absent.
4. Preferred assertion: `await tester.scrollUntilVisible(find.byType(ElevatedButton), 100)` followed by `expect(find.byType(ElevatedButton), findsOneWidget)`.

## Drag-Reorder Interaction Contract

**Widget:** `ReorderableListView.builder` inside a `SliverToBoxAdapter` per goal type section.

**Drag handle affordance:**
- Mobile (Android/iOS): `Icons.drag_indicator` at size 20, color `colorScheme.outlineVariant`, always visible. Touch target: `Padding(symmetric(horizontal: 8))` — minimum 36pt wide. Semantic label: `'Drag to reorder'`.
- Desktop: `Icons.drag_indicator` at default size, color `colorScheme.outline`, `AnimatedOpacity` at 0.6. Wrapped in `Tooltip(message: 'Drag to reorder')`. Size: `44×44` `SizedBox`.

**Priority chip behavior during and after drag:**
- During drag: chip shows the goal's current (pre-drop) weight. The drag ghost renders the goal card with existing state.
- After drop: `reorderAllWithPriority` writes new weights for all goals in the type group → `loadGoals()` → `notifyListeners()` → `Consumer<GoalsNotifier>` rebuilds → all `GoalCard` instances rerender with new `priorityWeight`. Chip label/color updates atomically.
- No intermediate state: there is no "pending" chip state. The chip transitions from old weight to new weight in the same frame as the `Consumer` rebuild.

**Cross-group isolation:** Drag is constrained within a goal type section (e.g. dragging within "Regular time" does not affect "Daily habits"). `_buildFullOrderedIds` reconstructs the full flat ID list for `reorderAllWithPriority` to compute weights globally, but only the dragged group's visual order changes.

**Stale chip failure mode (the bug PRIORITY-03 fixes):** If `GoalCard` is not inside `Consumer<GoalsNotifier>` (or is reading from a stale `Goal` object captured before the drag), the chip will not update. The executor must confirm the `GoalCard` receives its `Goal` from `notifier.timeTargetGoals` / `notifier.outcomeGoals` / `notifier.habitGoals` inside the `Consumer` — NOT from a local variable captured before `reorderAllWithPriority`.
