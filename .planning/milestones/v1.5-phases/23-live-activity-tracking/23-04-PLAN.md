<constraints>
1. **Serve a DEBUG build, not release.** `CLAUDE.md` is explicit: while the basics are still
   being worked through, diagnostics beat speed. A release build minifies every stack trace to
   `main.dart.js:<n>`, which is unreadable when something throws.
2. **Do not use `flutter run -d web-server`.** Its DDC incremental compiler fans the app out into
   ~866 module files; over tailscale latency the browser's ~6-connections-per-origin limit turns
   that into minutes of serial round-trips and a blank page. Build a single dart2js bundle and
   serve it statically.
3. **Use port 8123.** It already served the Phase 22 debug build (`22-UAT.md` line 25), so it has
   never carried a different build type — reusing it cannot create the service-worker collision
   `CLAUDE.md` trap #1 describes. `--pwa-strategy=none` also means this build never registers a
   service worker of its own.
4. **This plan changes no source code.** If the gate fails, stop and report — do not patch
   `lib/` from inside a verification plan. A failing gate means a defect belongs back in 23-01,
   23-02, or 23-03.
5. **Do not build an Artifact.** Host locally over the tailnet, per `CLAUDE.md`.
6. **A blank page is not automatically a broken build.** Rule out the two known false alarms
   (stale service worker; headless Chromium `CONTEXT_LOST_WEBGL`) before reporting a failure.
   Confirm in a real GPU-backed browser.
</constraints>
