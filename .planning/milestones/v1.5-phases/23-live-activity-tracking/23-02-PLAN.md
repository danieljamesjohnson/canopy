<objective>
Give the live row a real countdown: whole minutes rounded up while more than a minute remains,
seconds in the final minute — driven by a second, narrowly-scoped 1-second timer that exists only
during that final minute.

Purpose: LIVE-02 — time remaining in the current activity is shown and counts down while the
screen is open. Today the label already computes whole minutes, but it sits frozen at "1 min left"
for the entire last minute because the only ticker fires once a minute.

Output: one pure seconds-remaining helper, a two-branch label, and a lifecycle-managed fast timer
with the regression coverage that proves it does not leak.

**Locked decisions implemented here** (ID scheme defined in plan 23-01's objective; `D-01` is
`23-CONTEXT.md` decision 1, restated verbatim in `23-UI-SPEC.md` "Countdown granularity"):

| ID | Content | Where it lands |
|----|---------|----------------|
| D-01 | ≥60s → whole minutes rounded **up** ("3 min left"); <60s → seconds ("42s left"). Rounding up means a running activity never reads "0 min left". **Do not** replace the existing 1-minute `Timer.periodic` with a blanket 1-second timer — that is explicitly named as the lazy version of this decision and costs battery on a screen that is open all day. Run the coarse tick normally and escalate only while under a minute remains, then drop back. Any faster tick must be lifecycle-managed exactly like the existing one. | Task 1 (label), Task 2 (tick) |
| D-04 | Progress bar fills left-to-right across the activity's window | Task 1 — the bar is derived from the same seconds value as the label, so the two can never disagree |
| D-06 | Keep the injectable clock and use it for the <60s branch | Both tasks — every new clock read goes through `_nowFn` |

**Planner decisions made here:**

- **P-5 — one seconds computation, threaded down; not computed twice.** RESEARCH's recommended
  shape calls `_syncFastTimer(...)` from `build()`, but the seconds value it needs is computed
  inside `_buildLiveRow`. Rather than compute it in both places (a second derivation path, which
  is the exact class of bug Phase 22 spent a plan eliminating), this plan extracts one private
  helper `_liveSecondsRemaining(NowState)`, calls it **once** in `build()`, uses its result to
  drive `_syncFastTimer`, and threads the same `int?` down through `_buildTimelineRow` into
  `_buildLiveRow` for the label and the progress bar. One computation, one clock read, three
  consumers.
- **P-5a — resume re-checks the clock instead of blindly restarting.** RESEARCH requires that the
  fast timer only restart on resume if the live chunk is *still* in its final minute. Rather than
  duplicating that condition inside `didChangeAppLifecycleState`, the `resumed` branch triggers a
  rebuild, which re-runs the single `_syncFastTimer` decision against the fresh clock. This also
  fixes a real pre-existing staleness bug: today, resuming shows stale content until the next
  minute boundary.

**Why the existing minute math needs no rewrite.** RESEARCH derived that the current
`end - nowMinutes` expression is already algebraically identical to
`ceil(exact_seconds_remaining / 60)` for every positive remaining time, because `nowMinutes`
truncates seconds and `end` is always a whole minute. The "round up" half of D-01 is therefore
already satisfied today. The genuinely new work is only: (a) get second-level precision out of
`_nowFn()`, (b) branch the label format below 60s, (c) make the display actually refresh at 1 Hz
during that final minute. Task 1 keeps the ceil semantics — now expressed explicitly — and adds
boundary tests that lock the behaviour in rather than leaving it as an unasserted derivation.
</objective>

   `ValueListenableBuilder`, no `AnimationController`, no self-ticking countdown widget. The card
   receives `remainingLabel` as an injected string by contract (its doc comment, lines 8-11).
   Making it derive its own remaining time creates a second computation path.

   seconds is the failure mode D-01 names explicitly. `_fastTimer` is an addition, not a
   replacement (RESEARCH Pitfall 3).
4. **Never call `DateTime.now()` inside `_TodayScreenState`.** All clock reads go through
   `_nowFn` — that is what makes the countdown testable without real sleeps, and a prior review
   already fixed one drift from it (commit `1035339`).
5. **Never use `Future.delayed` or a real sleep in a test.** Drive time with
   `tester.pump(Duration)` against the injected clock. A real-sleep countdown test hangs the
   runner for up to a minute per assertion instead of failing cleanly.
6. **Every `Timer` created must be cancelled before the widget tree is disposed.**
   `flutter_test` fails with "A Timer is still pending even after the widget tree was disposed"
   otherwise, and that failure will surface in the *next* test, not the one that leaked.
7. **No new dependencies.** No `fake_async` package — `flutter_test`'s binding already provides
   fake-clock `pump()` semantics, which the existing timer/lifecycle test at
   `today_screen_now_state_test.dart:635-746` already relies on successfully.
8. **Formatting:** run `dart format` only on this plan's two files.
