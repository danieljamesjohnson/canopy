## Spacing Scale

Not applicable. No new layout is introduced. The long-break `Card` (`chunk_card.dart`
`_buildLongBreak`, margin `vertical: 4, horizontal: 16`, internal padding `16`) and the
short-break pill (`_buildShortBreak`, height `48`, margin `vertical: 2, horizontal: 16`)
are reused unmodified — a denser cadence changes *how many* of these cards render, not
their internal spacing.

**Visual-consequence check (asked for by scope note):** on a low-mood day the cadence
tightens from every-3 (current) to roughly every-2 chunks (BREAK-01). Reading
`chunk_card.dart`, the long-break card is a plain `Card` in a `ListView` with no
accordion/collapse behaviour — going from "every 3rd row" to "every 2nd row" is a change
of degree, not of kind; the existing rhythm already tolerates adjacent break cards (a
short break always follows every chunk regardless of the long-break cadence, per BREAK-02
"only the cadence count changed, not the break structure"). **No new break treatment is
required.** If a plan is tempted to add a "collapse consecutive breaks" affordance to
compensate, that is out of scope for this phase — flag it as a future polish item instead
of building it here (see CLAUDE.md: this app stays deliberately simple).

## Copywriting Contract

This is the substantive contract for this phase (TONE-01).

### The string being removed

`lib/services/schedule_generator.dart:190`, inside `_timeTargetRationale`:

```dart
return '${remaining.toStringAsFixed(1)}h behind this week';
```

This must not appear anywhere, in any form (including refactors that move the string
elsewhere in the file).

### Full replacement rationale set for `_timeTargetRationale`

`_timeTargetRationale` is the **only** place "behind this week" appears anywhere in the
codebase (confirmed by grep — no other user-facing string uses "behind"; the two other
"behind" hits in `lib/` are a code comment describing sort order and an unrelated timestamp
comment in `theme_notifier.dart`, neither user-facing, both out of scope). It is called
from four call sites (schedule_generator.dart:424, 456, 497, 523) — all four already
route through this one helper, so a single change covers every emission point.

`remaining` is computed exactly as today (unchanged — TONE-01 is copy-only):
`remaining = (goal.weeklyHourBudget - completedHrs this week).clamp(0.0, ∞)`.

| Condition | String | Notes |
|---|---|---|
| `remaining < 0.1` | `On track this week` | **Unchanged.** This is the existing sibling branch (line 189) and is the voice model TONE-01 must match — do not touch it. |
| `remaining >= 0.1` | `Working toward ${remaining.toStringAsFixed(1)}h this week` | Replaces the deficit string. Same `toStringAsFixed(1)` formatting as before (e.g. `Working toward 2.5h this week`, `Working toward 0.3h this week`). |

Rationale for the specific wording: `Working toward your goal` is already the established
rationale string for outcome goals (`_outcomeRationale`, line 171, unchanged by this
phase). Reusing the "Working toward …" verb phrase for the time-target case is not a new
voice — it's the app's own existing pattern for "this chunk exists because of ongoing
effort," applied consistently, with the hour figure filled in. It reads as what today's
schedule is doing *for* the goal (an amount of time being worked toward), not as a report
of the user's shortfall — satisfying TONE-01's "what the schedule is doing for the user,
not a deficit report."

**Do not** introduce any of these words/framings into the replacement or into any other
schedule/rationale copy in this phase's diff: "behind", "short", "owe(s)", "missed",
"failing", "catch up", "deficit", or any percentage/comparison-to-target framing. (This
mirrors the standing contract already locked for Phase 22/23's copy — see
`.planning/phases/22-unified-today-screen/22-UI-SPEC.md` and
`.planning/phases/23-live-activity-tracking/23-UI-SPEC.md` — so the voice stays consistent
across the whole v1.5 milestone, not just this phase.)
