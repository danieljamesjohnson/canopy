### New in Phase 11 — Donut Slice Colors

These are the only net-new color decisions in this phase.

| Slice | Color Value | Rationale |
|-------|-------------|-----------|
| Commitments slice | `const Color(0xFF607D8B)` — Blue-Grey 500 | Neutral, professional; does not compete with goal colors from `GoalsNotifier.colorPalette`; distinguishable from all 8 palette entries; matches the existing `#607D8B` entry in the palette but used exclusively for the Commitments system role |
| Other (catch-all) slice | `const Color(0xFFBDBDBD)` — Grey 400 | Clearly residual/uncategorized; low visual weight; does not appear in the 8-color goal palette; readable as a legend dot against both light and dark surfaces |
| Time not spent slice | `theme.colorScheme.outlineVariant` | UNCHANGED — already implemented in `donut_chart.dart` line 60; matches Phase 5 D-02 decision |
| Archived-goal slices | Goal's stored `color` hex (via `hexToColor(goal.color!)`) — fallback: `GoalsNotifier.colorPalette[i % palette.length]` | Same color logic as active goals; archived goals keep their original color so the legend is recognizable to users who remember the goal |

Notes:
- The Commitments slice color `#607D8B` is already in `GoalsNotifier.colorPalette` at index 7. The executor MUST NOT assign index-7 palette color to an active goal AND simultaneously use it for the Commitments slice in the same chart render — the contract is that `#607D8B` is reserved as the Commitments system color. In practice, slice color resolution for active goals uses index % palette.length against the ACTIVE goal list; the Commitments slice always uses the hardcoded `const Color(0xFF607D8B)`, so visual collision is possible only when the 8th active goal would also get index 7. Acceptable risk in v1 given the rarity of 8+ active goals — document this in a code comment.
- If both `#607D8B` and `#BDBDBD` prove insufficiently distinct in practice during UAT, the fallback for Other is `const Color(0xFF9E9E9E)` (Grey 500) which has higher contrast.

## Donut Chart Slice Contract

This is the primary visual contract change in Phase 11. The executor references
this section as the source of truth for `donut_chart.dart` reconstruction.

### Slice Order (top of pie, clockwise)

1. Active goal slices — one per active goal, in `goals` list order (sortOrder ascending)
2. Archived goal slices — one per archived goal with any completions in the period, sorted alphabetically by name
3. Commitments slice — single aggregated slice (all commitment-attributed logs)
4. Other slice — any logged goalId that resolved to neither an active goal, archived goal, nor commitment
5. Time not spent slice — skipped + deferred count (existing D-02 behavior)

Slices with `value == 0` are OMITTED from both `sections` list and `legendEntries`. A zero-value slice produces a 0dp arc that can confuse `PieChart` layout — exclude it. The "Other" and "Commitments" slices are only added when their count > 0.

### Legend Row Format

Each legend row renders identically to the existing pattern:
`CircleAvatar(radius: 6, backgroundColor: color)` + 8px gap + `Expanded(Text(label, style: bodySmall, overflow: ellipsis))` + `Text('${pct.toStringAsFixed(0)}%', style: bodySmall, color: onSurfaceVariant)`

Legend label strings:
- Active goal: `goal.name` (unchanged)
- Archived goal: `'${goal.name} (archived)'` — space, parenthetical suffix, no special casing
- Commitments: `'Commitments'` — title case, no additional suffix
- Other: `'Other'`
- Time not spent: `'Time not spent'` (unchanged)

### Percentage Calculation

`pct = count / totalValue * 100` where `totalValue` is the sum of ALL drawn slice values (active + archived + commitments + other + notSpent). The denominator must include every drawn slice so percentages sum to 100%. The existing `totalValue` calculation in `donut_chart.dart` line 36 must be expanded to include the new slice counts before the percentage division loop.

### Legibility Requirement

All slice labels in the legend must be readable: `overflow: TextOverflow.ellipsis` on the `Expanded` label text (already implemented). The `(archived)` suffix is part of the truncation domain — if the goal name is very long, ellipsis may clip the suffix; this is acceptable.

## Adjustments Section — Priority Write-Back Contract

The drag-reorder list in `AdjustmentsSection` currently calls `notifier.reorderAll(orderedIds)` which writes `sortOrder` only. Phase 11 must also write `priorityWeight` so the schedule generator picks up the change.

### Linear-Spread Formula

Given `n` goals in the reordered list (index 0 = top = highest priority):

```
priorityWeight[i] = high - (high - low) * i / (n - 1)   when n > 1
priorityWeight[0] = high                                  when n == 1
```

Where:
- `high = 0.75` (existing "High" sentinel from ENGINE-06 SegmentedButton)
- `low  = 0.25` (existing "Low" sentinel from ENGINE-06 SegmentedButton)

This produces distinct, monotonic weights: top goal = 0.75, bottom goal = 0.25, middle goals distributed linearly. When `n == 1`, the single goal gets 0.75.

The formula intentionally reuses the existing High/Normal/Low bounds so the generated weights are within the range the schedule generator already expects from ENGINE-06.

### Interaction: no UI change

The drag-reorder tile (`GoalAdjustmentTile`) is visually unchanged. The only change is that "Finish review" (the existing `_finish()` CTA in `AdjustmentsSection`) also writes `priorityWeight` values derived from the final drag order, in addition to the existing `sortOrder` write. No new affordance, tooltip, or visual indicator is required for this change — it is a silent correctness fix, not a user-visible feature.
