<objective>
Wire the review screen to load its own data on a cold launch (REVIEW-03) and swap the adjustments call site to the priority-writing method (REVIEW-02 end-to-end), consuming the DonutChart/DataSection signature and `reorderAllWithPriority` introduced in Plan 01.

REVIEW-03 root cause: `_loadData()` reads only active goals from `GoalsNotifier` and never loads archived goals or commitment blocks, so on a true cold launch direct to `/review` the commitment and archived-goal logs cannot resolve; additionally the empty-state guard `totalCompleted == 0 && goals.isEmpty` ties "no review data" to provider goal-list state instead of the review's own logs. Fix: capture `GoalsNotifier` and `CommitmentsNotifier` refs before any await, load archived goals via `getArchivedGoals()` and commitment blocks via `CommitmentsNotifier.blocks`, change the guard to `allLogs.isEmpty`, store both lists in state, and pass them into `DataSection`.

REVIEW-02 wiring: `AdjustmentsSection._finish()` currently calls `reorderAll(orderedIds)` (sortOrder only). Swap to `reorderAllWithPriority(orderedIds)` so finishing the review persists `priorityWeight`; the next generation cycle picks it up (today's schedule is intentionally NOT regenerated).

Purpose: The review loads correctly from a cold launch and its priority adjustments become a durable generation input.
Output: Updated screen + adjustments call site + a cold-launch regression widget test.
</objective>

<threat_model>
## Trust Boundaries

Local-only single-user Flutter app — no network, no auth, no backend, no LLM API, local Hive storage only. The trust boundary is in-process: persisted Hive data (logs, goals, commitments) → the review's `_loadData` read path → DataSection/DonutChart render and the persisted priorityWeight write on finish. Data-integrity, not external attack, is the realistic surface.

| Boundary | Description |
|----------|-------------|
| Hive logs/goals/commitments → _loadData | A cold launch must resolve every logged id, else commitment/archived time silently disappears from the review |
| Finish review → persisted priorityWeight | A finish that calls the wrong (sortOrder-only) method leaves generation unchanged |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-04 | Tampering | _loadData cold-launch resolution | mitigate | Load archived goals + commitment blocks so every logged id resolves; empty-state keyed on allLogs.isEmpty (own data), not provider state; Task 1 cold-launch test asserts active/archived/commitments render without prior tab visit |
| T-11-05 | Repudiation | append-only quarterly snapshot history | mitigate | _finish() preserves the existing CR-02 append-only snapshot path (append a new snapshot, no overwrite/id-reuse); this plan does not alter snapshot construction beyond the reorder-method swap |
| T-11-06 | Tampering | _finish priorityWeight persistence | mitigate | Call reorderAllWithPriority (Plan 01) instead of reorderAll; the Plan 01 generator-ordering + notifier weight tests prove the write reaches generation; today's schedule is intentionally not regenerated (next-day pickup) |
| T-11-SC | Tampering | npm/pip/cargo installs | accept | No packages added this phase (RESEARCH Package Legitimacy Audit: none introduced); no install tasks, no slopcheck checkpoint required |

No high-severity external (web/auth/network) threats exist in this phase — milestone constraints forbid network and AI surfaces.
